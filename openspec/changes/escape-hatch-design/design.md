## Context

irisoutのコンパイラは、受理しないパターンに当たると`compile:`+
`(scope limit)`エラーで拒否する(ADR-0004: ソースが要求する以上の実行を
生成しない、その裏面として「安全に拒否する」)。この設計自体は正しいが、
現状は1つの`scope limit`がコンポーネント全体のコンパイルを止める。
アプリが少しでもコンパイラのカバー範囲外のパターンを必要とすると、
コンパイラが完成するまでアプリ全体が書けない。

ADR-0008は、authoring APIを「変数ゾーン→UIゾーン→動きゾーン」の3構造
(constのみ/render()マーカー/function宣言)に固定し、ハンドラは動きゾーンの
function宣言へJSX側から識別子参照する形をとる、という前例がある。この
配線パターン(識別子参照 + 巻き上げfunction宣言)は「型・rename・
go-to-defが効く」という理由でハンドラ配線に採用された経緯があり、
escape hatchの配線にもそのまま転用できる可能性がある。

## Goals / Non-Goals

**Goals:**
- 「共存の単位」(コンポーネント全体か、UI木の中の1要素か、専用の
  ゾーンか)を決定する。
- 決定した単位について、authoring API上の記法とコンパイラ側の受理・
  生成ルールを定義する。
- ADR-0004(統治原則)・ADR-0008(ゾーン構造)との整合性を確認する。

**Non-Goals:**
- 実装(`src/`の変更)そのもの。決定内容に基づく実装は別changeで行う。
- 手書きJS側の状態とirisout側のsignal/derivedとの双方向同期。escape
  hatchは「その部分をirisoutの管理外に置く」ことが前提で、同期機構を
  持ち込むとADR-0004の「ソースが要求していない実行時機構を足さない」
  に反する。

## Decisions

### 1. 共存の単位: JSX要素1つ(要素単位)

3つの単位を検討した:

| 単位 | 影響範囲 | 既存パターンとの整合性 | 却下/採用理由 |
|---|---|---|---|
| (a) コンポーネント全体 | そのコンポーネントは丸ごとirisout管理外 | ゾーン構造と無関係になる | コンパイラのカバー範囲が1箇所広がるたびの効果が薄い。「1パターンがページ全体を止める」問題を「1パターンがコンポーネント全体を止める」に縮小するだけで、UNRESOLVED(06)/(07)のような「アイテム内の一部だけ手書きにしたい」ケースを解決できない |
| (b) 新しい専用ゾーン(例:「手書きゾーン」) | ゾーン構造に第4のゾーンを追加 | ADR-0008の3ゾーン構造(変数→UI→動き)を拡張する | ゾーンはコンポーネント直下の構造を表すもので、「UI木の特定の1箇所」という局所的な話とは粒度が違う。UI木の途中に手書き部分を挟みたいケース(M5のUNRESOLVED(06)/(07)相当)を表現できない |
| (c) JSX要素1つ(採用) | UI木の任意の位置に置ける | ADR-0008の「識別子参照+巻き上げfunction宣言」パターンをそのまま転用できる | ブラスト半径が最小。1箇所の未対応パターンだけをピンポイントで手書きに逃がせ、他の部分はirisoutの管理下に留められる。M5のネストした構造ユニット(UNRESOLVED-06/07)の暫定的な逃げ道にもなりうる |

採用: **(c) JSX要素1つを単位とする**。

### 2. 記法: 専用マーカー要素 + 動きゾーンへの識別子参照

ADR-0008のハンドラ配線(`onClick={handleCountUp}`、識別子参照→
`render()`より後ろのfunction宣言)と同型の配線にする:

```jsx
render(
  <div class="widget">
    <Escape mount={setupLegacyWidget} />
  </div>
)

function setupLegacyWidget(container) {
  // container は<Escape>の位置に生成されたDOM要素(コンパイラは
  // この中身を一切解釈しない)。ここから先は手書きvanilla JS。
  container.textContent = '...'
  container.addEventListener('click', () => { /* ... */ })
}
```

- `<Escape mount={identifier} />`はコンパイラが特別扱いする組み込み
  マーカー要素(`render`/`signal`と同様、ビルド時に消えるイディオム)。
- `mount`属性は、ハンドラと同じ「`render()`より後ろのfunction宣言への
  識別子参照」ルールに従う(ADR-0008 決定の再利用)。
- コンパイラは`<Escape>`の位置に空のコンテナ要素(例: `<div>`、または
  テキストマーカーと同じコメントアンカー方式)を1つ生成し、マウント時に
  `mount(container)`を1回呼び出すコードを生成する。それ以外の解釈は
  一切行わない(中身のJSX/式は書けない ― `<Escape>`は常に自己完結
  タグで、子要素を持てない)。

### 3. teardownは今回作らない

ADR-0005決定4(アイテムteardown不要)と同じ理由: `mount`が登録した
リスナー・状態は、コンテナDOM部分木がkeyed reuseやリスト削除で`remove()`
された際、DOM部分木ごとGC対象になる。ADR-0004の「使われていない機構は
作らない」に従い、明示的な`unmount`コールバックは今回の設計に含めない。

### 4. リストアイテム/条件分岐ブランチ内での使用

`<Escape>`はリストアイテム・条件分岐ブランチのfactory関数内にも置ける
(M5実装後)。この場合、`mount`はそのインスタンスごとに1回呼ばれる。
これはM5のUNRESOLVED(06)/(07)(ネストした構造ユニット)に対する、
コンパイラ側の一般化された対応を待たずに使える暫定的な逃げ道になり
うるが、本changeではその活用方法の確定までは踏み込まない(M5側の
follow-up changeで判断する)。

### 5. mount関数本体は追跡宣言に触れられない(compile errorで拒否)

Non-Goals(signal/derivedとの同期はしない)の強制。mount関数の本体は
不透明(解析しない)だが、生成コードではsignal/derivedはプレーン変数に
なるため、本体が`count()`のような追跡宣言への参照を含むと実行時に
TypeErrorで静かに壊れる。ADR-0007と同じ「安全に拒否」に従い、コンパイラは
mount関数本体に識別子スキャンのみを行い、追跡宣言(signal/derived)への
参照を見つけたらcompile error(scope limit)で拒否する。状態と連動する
振る舞いが必要な場合は`use=`(change `action-use-attribute`)を使う。

### 6. `use=`(element-use-action)との役割分担

`<Escape mount>`と`use=`は同じ配線(識別子参照+要素を引数に受ける関数)
の2変種で、区別は1軸: **本体をコンパイラが解析するか**。`use=`は解析
される(signal読み書き可、返り値クロージャがリアクティブ配線される)、
`<Escape>`は不透明(追跡宣言に触れられない)。一言で言えば「`use=`は
irisoutの世界の中で要素に振る舞いを足す。`<Escape>`はirisoutの世界の
外に出る」。この1軸は両方のADRに明記する。

## Risks / Trade-offs

- [escape hatch内は完全にコンパイラの管理外になるため、CONCEPT.v2.mdの
  「熟練開発者が手で書くなら」という基準がescape hatch内部には及ばなく
  なる] → 意図通り。escape hatchは「irisoutの管理下に置けない部分を
  明示的に区切る」ためのものであり、区切った外側(irisoutが生成する
  大部分)の保証は変わらない。
- [`<Escape>`が濫用され、本来コンパイラで表現できる部分まで手書きに
  逃げてしまう] → 本ADRのスコープ外の運用上の懸念。必要なら将来lintで
  警告する(今回は作らない、ADR-0004「使われていない機構は作らない」)。
- [新しいマーカー要素の追加はauthoring APIの表面積を増やす] → ADR-0008で
  確立した「識別子参照+巻き上げfunction宣言」のパターンをそのまま
  再利用するため、authoring者が新しく覚える概念は「`<Escape>`という
  組み込みタグがある」ことだけで最小限。

## Open Questions

- `<Escape>`という名前が最終的な採用名かは、ADR起票時に再検討する
  (例: `<Raw>`、`<Handwritten>`等の代替名)。
- M5のUNRESOLVED(06)/(07)を`<Escape>`で暫定的に迂回する運用を正式に
  推奨するかどうかは、M5側のfollow-up changeで判断する。
