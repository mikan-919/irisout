# Vanillaの実装から確認した不足（2026-10-16）

対象は[上流のMain.js](https://github.com/krausest/js-framework-benchmark/blob/bf894b681fb56433ccb6efb4a3c93e35eda2b20d/frameworks/keyed/vanillajs/src/Main.js)、irisoutの`e26ebc9`時点の生成物、コンパイラ、実行時処理である。コードの読取りと、同じ生成物への呼出し回数の計装を行った。速度の再測定や製品実装の変更は行っていない。

不足しているのは、作成時だけ必要な参照を残さない解析、位置が分かっている更新のDOMへの接続、全置換を再利用の照合から分ける処理である。直接イベント配線も費用の原因になる。これらを一つの原因へまとめない。

## 1. 作成後に使わない参照と、不変のキーの表示値を保存している

Vanillaの`createRow`は行のDOM要素を返し、`Main.rows`へ格納する。データは`Store.data`と`Main.data`の配列から参照する。irisoutは行データとは別に`FlatListRecord`と描画用オブジェクトを各1個作り、Mapへ登録する。1,000行なら追加の管理用オブジェクトは2,000個になる。この件数にDOM内部や配列自体の確保は含めない。

irisoutの圧縮後の生成物にも、描画用オブジェクトの次の6フィールドが残っていることを構文解析で確認した。文字列・属性の保存値は、この後さらに代入される。

```js
{ el, value: row, m6, m7, m9, m8 }
```

`m8`は削除リンクで、生成時のイベント登録と行情報の接続に必要だが、以後の表示更新には使わない。`m9`は`el`と同じ行要素である。`m6`は識別子のセルで、対応する`text_m6`にも識別子の表示文字列を保存する。今回のキーは`row.id`なので、同じキーで再利用する行の識別子は変わらない。キーが自身のプリミティブ値である条件を使えば、通常更新の識別子比較と、そのためだけの参照・保存値を省く候補になる。

現状の[生成処理](../../compiler/src/codegen.ts)は本文・属性・イベントの参照を同じ集合へ入れ、その全参照を描画用オブジェクトへ保存する。作成用と更新用の参照の寿命を分けていない。先に`m8`の保存と`m9`の重複を除き、次にキー不変の証明を更新関数へ伝える順で検証できる。管理用オブジェクトの統合は、その後の設計候補となる。

## 2. 添字を使う更新が、途中でキー検索へ戻っている

Vanillaの`update`は`i += 10`で対象を選び、`rows[i]`から表示へ書く。交換も`rows[1]`と`rows[998]`を使い、DOMを2回動かす。

irisoutは部分更新の対象添字をコンパイル時に確認できているが、`mapListValues`は変更前後の行を組にして記録し、`reconcileListMap`でIDからMapを100回引き直す。1,000参照の配列複製、100個の新しい行、100個の変更の組、変更フィールドの判定、100回の表示値比較も残る。交換は全件照合を除けたが、基点・交換結果・親の照合と2回のMap検索が残る。

不足は、添字と描画対象の対応を保ち、証明できる更新をその対応へ接続する処理である。添字順の表を別に持つ場合はメモリが増えるため、既存の管理情報との統合も比較する必要がある。新しい行の確保を除くには、イベント中の古い行参照を保つ条件も追加検証する。配列複製だけを省いた前回の案で速度改善がなかったことは、この経路全体の削減が不可能だという結果ではない。

ただし、VanillaもText節点を保持していない。更新ごとに`rows[i].childNodes[1].childNodes[0].firstChild`を辿る。今回の計装では100行更新で`childNodes`を200回、`firstChild`を100回参照した。irisoutは保存済みのラベル要素から`firstChild`・`nodeType`・`lastChild`を各100回参照する。DOM参照回数だけを見て、irisoutだけが探索しているとは言えない。配列・行・変更記録・Map検索・比較の差を別に見る必要がある。

## 3. 全置換でも混合更新のMapを照合している

Vanillaの`run`・`runLots`は旧DOMと配列を空にしてから新しい行を作る。irisoutの[通常照合](../../runtime/src/index.ts)は新しい各キーをMapで検索・登録し、全キーが新しい場合も、新旧の記録が入ったMapを走査して旧記録を削除する。1,000行置換の呼出しはMap検索1,000回、登録1,000回、削除1,000回となった。走査自体は、この場合は新旧合計2,000記録を対象とする。

新しいキー集合が既存と交わらないことを証明・確認し、全置換を混合更新から分ける余地がある。現在はその情報がないため、使わない旧記録との照合と、新旧DOM・管理情報の同時保持が発生する。

Vanillaの「先に消す」順序をそのままコピーすると、生成関数やDOM作成で例外が起きた場合、カスタム要素や同期処理が再入した場合の観測が変わり得る。全置換の判定と、破棄してよい時点の証明は別に必要である。

## 4. 行の運び方が異なり、従来の計装では途中の追加が見えていなかった

Vanillaの`appendRows`は、空なら`tbody`自体を文書から外し、そこへ直接行を追加して最後に戻す。既存行への追加では、接続した`tbody`へ直接追加する。irisoutは`DocumentFragment`（DOMへ渡す節点の一時的な入れ物）へ行を入れ、最後に親へ挿入する。

| 1,000行の操作  | Vanilla                                             | irisout                                            |
| -------------- | --------------------------------------------------- | -------------------------------------------------- |
| 作成           | `tbody`を外す1回、`appendChild`1,000回、親へ戻す1回 | 断片作成1回、`fragment.append`1,000回、親へ挿入1回 |
| 既存行への追加 | `appendChild`1,000回                                | 断片作成1回、`fragment.append`1,000回、親へ挿入1回 |
| 全削除         | `tbody.textContent = ''`                            | 境界確認、`replaceChildren`、Mapの一括消去         |

従来の計装は`DocumentFragment.append`を数えておらず、irisoutの途中の追加1,000回が集計に出ていなかった。今回追加した[生値](./vanilla-code-work.json)には含めた。追加回数が少なく見えていたことを、実際の作業が少ないことへ読み替えない。

挿入された各節点は断片から最終的な親へ移る。ただし、ネイティブ内部の費用はJavaScriptの呼出し回数から求められない。上流コードには断片を使う方が遅かったというコメントがあるが、現在のブラウザーでの速度の証明には使わない。両方式の比較測定と、境界コメント・カスタム要素・再入の検証が必要である。

## 5. 直接イベント配線は、登録以外の探索・保存も増やしている

Vanillaは初期化時の親への2件の登録でボタンと行のクリックを処理し、行作成時の登録は0件である。irisoutは1,000行作成中に2,000件登録し、イベント対象へ行情報も接続する。

Vanillaの`createRow`は識別子とラベルの設定に必要なDOMだけを辿り、削除リンクを探さない。irisoutは削除リンクの参照を作るため、行ごとに`nextElementSibling`2回と`firstElementChild`1回を追加する。テンプレート初回準備の固定費を除く、行作成1行当たりの計装対象の参照は、Vanillaが5回、irisoutが8回である。irisoutの余分な3回は、この削除リンクの探索に対応する。ループ自体のJavaScript処理や保存値への代入は、この回数に含めない。

前回のイベント登録省略実験は、登録だけを止め、削除リンクの探索・行情報の接続・描画用オブジェクトの保存を残していた。その実験で確認した1,000行作成3.0350→2.6075ms、10,000行作成31.5525→26.8575msは、委譲する実装全体の時間ではない。探索と保持情報まで除いた効果は未測定である。

委譲はイベントを親で受け取る方式で、`currentTarget`、伝播、ほかの処理との順序が変わる。[ADR-0021](../../../docs/adr/0021-list-item-event-delegation.md)の契約を維持したままVanillaの配線へ置き換えることはできない。契約を維持して行う参照・保存の削減と、契約を別に定める委譲は分けて判断する。

## 優先順と検証範囲

先に、作成時だけの参照と根の重複保存を省き、キー不変の情報を生成側へ伝える。次に管理用オブジェクトの統合、更新添字と描画対象の接続、全置換の専用経路を検証する。挿入方式とイベントの契約変更は、それぞれ比較測定を行って判断する。

今回確認したのはコード構造と呼出し回数であり、新しい高速化の達成報告ではない。計装は`DocumentFragment.append`、`createDocumentFragment`、`Node.childNodes`を追加した一度の全9操作で、時間には使っていない。VanillaとirisoutのスクリプトのSHA-256を生値に保存した。製品側のコードは変更していない。
