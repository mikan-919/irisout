# 試用Bの独立操作確認

対象は http://127.0.0.1:4317 の新規アプリ。実装ソース、試用Bの記録、過去の報告は読んでいない。課題と前回の検査コードを使い、HTTPと画面を確認した。既存検査器は7/8合格、追加検査は8/8合格。既存検査器の項目7は受信数の探索方法とDOM表記の不一致で停止した。追加検査で同じ動作条件を満たすことを確認した。ブラウザー例外は両検査とも0件。

| 課題                         | 既存検査         | 追加確認と判定                                                                                                                                                  |
| ---------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 一覧・詳細の初期HTML       | 合格             | JavaScript無効で一覧の3件と全詳細の件名を表示。HTTP 200。合格。                                                                                                 |
| 2 初期API・未知ID            | 合格             | 開始時はi1/i2/i3がすべて未解決。未知IDは404。合格。                                                                                                             |
| 3 検索の競合                 | 合格             | 決済601ms、通知31ms。追加検査では通知200の566ms後に決済200を受信しても通知だけを表示。合格。                                                                    |
| 4 503と回復                  | 合格             | 状態表示は「検索失敗 (503)。検索語を変更してください。」。完了・成功・更新しましたの表示なし。次の通知検索で失敗表示が消えた。合格。                            |
| 5 解決と再読み込み           | 合格             | 既存検査でi1、追加検査でi2を更新。Spaceで解決ボタンを実行でき、一覧・一覧の再読み込み・詳細の再読み込み・APIに反映。合格。                                      |
| 6 ID別メモ                   | 合格             | 既存検査はi1/i2、追加検査はi2/i3の値を分離し、一覧への往復と再読み込み後も保持。合格。                                                                          |
| 7 監視の登録・解除           | 探索不一致で停止 | ラベル「受信数」の出力値は各詳細で0→1。同じ文書で登録数0→1→0→1→0、追加・解除は各2回。動作は合格。                                                               |
| 8 未応答中の遷移・キーボード | 合格             | 追加検査で要求から59ms後に詳細へ到達し、この時点では未応答。後に200を受信してもURL・件名・作業メモを維持。Tab、Enter、Spaceで検索・リンク・ボタンを操作。合格。 |

項目7の再現は、一覧からi1の「詳細」を開き、`incident-ping`を1回送信する。画面本文は送信前が「監視中 0」、送信後が「監視中 1」。受信数は `<output aria-label="受信数">0</output>` で示されている。既存検査器は本文に対し `/受信数\s*[:：]\s*0\b/` を要求するため、「詳細の受信数が0から始まりません」で停止する。これはアプリの受信処理の失敗ではない。追加検査は出力欄をラベルで探索し、送信前0・送信後1と、監視の追加・解除をそれぞれ確認した。判定条件は緩めていない。

比較条件は前回と同じ課題、URL、Chromium、既存検査器、1280×900の画面、初期状態からの検査順序である。既存検査器は変更していない。追加検査は前回のコードを再利用し、DOMに合わせて2点だけ探索方法を変更した。通知遅延の一覧項目は見出し要素の代わりに一覧項目内の件名とi2の詳細リンクで特定し、受信数は本文表記の代わりにラベル付き出力値で読み取った。要求の未応答、実際の200応答、同一文書、登録数、保存後の値などの条件は同じである。

実DOMでは一覧件名「決済API停止」はLI直下のSPANで、リンクの役割はない。別の「詳細」リンクが各IDにある。検索はラベル「検索」のINPUTで、前回はtype=search、今回はtype=text。今回は上部に一覧へのリンクがあるため、初期位置から検索へのTabは2回、詳細から解決ボタンへのTabも2回だった。受信数の表記差と見出し要素の差以外に、今回の追加検査で動作の差は観測していない。

検査回数は既存検査器1回、追加検査1回。アプリと本体は変更していない。試験によりi1/i2は解決済み。相対import、Honoのloader、`use=`の記述、依存版、型検査、本番構築は画面とHTTPから確定できないため未判定。

証拠は `result.json`内の`existing`と`additional`。画面は `existing/failure-7-0.png`、`search-race.png`、`search-503.png`、`pending-detail.png`。追加検査の再現コードは `additional.mjs`。
