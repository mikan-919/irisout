# yt-utilをirisoutとHono RPCへ移す実装計画

作成日: 2026-09-13。実装は未着手。この文書は移植の作業計画であり、irisoutの新しい公開仕様を確定するものではない。

## 目的と前提

既存のyt-utilを、画面はirisout、サーバーはHono、通常の取得・更新はHono RPCという構成へ移す。プレイリストを取得し、類似度による視聴順を生成し、YouTubeへ書き出す既存の用途を維持する。この移植で必要になった接続処理を材料に、irisoutのフルスタック対応を判断する。

調査元は`/home/nixos/ghq/github.com/mikan-919/yt-util`の作業コピーである。GitHub経由では取得できなかった。基点は`ae357e7b2287ac81552eee26358141114e425bc7`だが、認証・YouTube操作・ページ・試験に未コミットの変更があり、調査はその変更を含む。実装開始時に差分を再確認し、Jujutsuで保存してから別の作業コピーを用意する。既存変更を上書きしない。

実装先はyt-utilの移植用作業コピーとする。irisoutリポジトリへアプリ本体を取り込むことは初期案に含めない。個人利用・自己管理のサーバーという対象範囲、既存のデータベース構造、認証方式を維持する。本番の最初の検証環境はBunとし、現在のVercel向け配信との同等性は別に検証する。

## 構成と責務

| 部分         | 方針                                                                  |
| ------------ | --------------------------------------------------------------------- |
| 画面         | irisoutの静的HTML、`signal`・`derived`、一覧・条件分岐で構成する      |
| 通常の通信   | Honoの経路型を`hc<AppType>`へ渡す。独自RPC変換は作らない              |
| 認証         | Better Authを維持し、要求のヘッダーからセッションを取得する           |
| サーバー処理 | YouTube通信、所有権確認、類似度計算、保存をHonoの経路から呼ぶ         |
| 永続化       | DrizzleとlibSQLの既存処理・識別子・表構造を再利用する                 |
| 進捗通知     | 埋め込み生成・書き出しはSSEを維持する                                 |
| 開発         | Vite+、`irisout/vite`、Honoの開発用接続を一つの起動コマンドへまとめる |
| 本番         | Bun上のHonoがAPIとビルド済み画面を同じオリジンで配信する              |

注: Hono RPCはHTTP経路の入力・出力型を共有する方式で、サーバー関数を直接実行する仕組みではない。応答状態と通信失敗を呼び出し側で扱う。SSEはサーバーから進捗を継続送信する方式であり、JSONの戻り値とは別にイベント形式と途中終了を定義する。同じオリジンとは画面とAPIの方式・ホスト・ポートが同じことで、認証Cookieの接続を検証しやすくする。

| `src/lib/schema.ts`、`db.ts`、`drizzle/`                | 表構造と移行履歴を維持し、試験は複製したデータベースで行う           |
| `src/lib/api.ts`                                        | `next/headers`・`NextResponse`への依存をHonoの要求・応答へ置き換える |
| `src/app/api/`                                          | Honoの経路へ移す。認証とプレイリスト所有権の検査を残す               |
| ページ内のサーバーデータ取得                            | 一覧・詳細の取得APIへ移し、読み込み中と失敗時の画面を用意する        |

| CSS・画像・アイコン                                     | 再利用できる資源を残し、React依存のアイコンをSVG等へ置き換える       |

## 実装順序と各段階の完了条件

### 0. 移植基点と比較条件を保存する

- [ ] yt-utilの指示、未コミット差分、依存版、既存試験結果を記録し、移植用作業コピーを用意する。
- [ ] 現行画面のログイン、一覧、検索、選択、視聴済み、並べ替え、適用、書き出しの挙動を記録する。
- [ ] 同一動画の重複を含むプレイリストを試験用データに含める。動画IDとプレイリスト項目IDを区別する。
- [ ] 同じデータとブラウザで、一覧の初期表示時間・スクロール・操作応答を比較できる条件を保存する。

完了条件: 移植元の変更が保存され、既存不具合と移植による不具合を区別できる。秘密情報や実データは試験用資料へ書き出さない。

### 1. irisoutとHono RPCの接続を検証する

- [ ] 静的画面からHono RPCで試験用の一覧を取得し、irisoutの状態へ反映する。
- [ ] Vite+とHono開発用プラグインの併用を検証し、HTMLの変換と`/api/*`の担当を分ける。競合する場合はViteの代理転送とBunサーバーで同等の構成を検証する。
- [ ] サーバーの`AppType`を型だけ参照し、入力・成功応答・失敗応答の型検査を行う。サーバー実装をブラウザへ取り込まない。
- [ ] irisoutが相対`.js`・`.jsx`を解析する境界と、TypeScript製RPCクライアントの接続を確認する。Viteが処理する補助モジュールへの接続方法を実例で決める。
- [ ] `try/catch/finally`、進捗コールバック、非同期処理後の状態更新を最小例で確認する。失敗処理は通常の補助関数で扱い、状態への反映を対応記法へ接続する。
- [ ] 本番ビルドをBunで配信し、URLの直接アクセスとAPIへの接続を確認する。

完了条件: 一つの開発コマンドで画面とAPIが動き、本番生成物でも取得・失敗表示・再試行が動く。ブラウザ生成物にサーバーの認証・DB処理が含まれない。対応範囲が不足する場合は再現例を保存し、必要なirisout変更を別の仕様変更へ切り出す。

### 2. ログインから視聴済み保存までを通す

- [ ] Better Authの認証経路を接続し、ログイン・ログアウト・期限切れ時の再接続を実装する。
- [ ] プレイリスト一覧・詳細の取得と、視聴済み保存をHono RPCへ移す。
- [ ] 画面に読み込み中・空一覧・失敗・再試行を実装する。初期データはブラウザから取得する。
- [ ] 一覧、検索、動画選択、YouTubeへのリンク、視聴済み状態をirisoutへ移す。
- [ ] 視聴済み保存の失敗を表示し、失敗した変更が保存済みに見えないようにする。連続操作の応答順も検証する。

完了条件: ログイン後に自分のプレイリストを表示し、視聴済み変更が再読み込み後も残る。未認証・他人のプレイリストへの要求はサーバーで拒否される。画面切り替え後の古い応答が新しい画面を更新しない。

### 3. 並べ替えと一覧操作を移す

- [ ] 類似度計算と視聴順の保存を引き継ぎ、開始動画・視聴済み末尾への移動を確認する。
- [ ] 選択・検索・類似度表示・スクロール位置を新しい視聴順へ整合させる。
- [ ] いいね・削除の保留、取消、適用を移す。削除確認と、成功した操作だけ保留から除く挙動を維持する。
- [ ] 一覧の描画方式を比較する。全件描画で実用範囲を満たさない場合は表示範囲だけの描画を実装する。単にReact依存を消すために既存の一覧性能を落とさない。

完了条件: 固定入力の視聴順が移植前と一致し、部分失敗時も未完了の操作を判別できる。重複動画でも削除対象を項目IDで区別する。一覧性能は段階0と同じ条件で比較し、採用理由を記録する。

### 4. 埋め込み生成と書き出しを移す

- [ ] Gemini側の生成・既存の利用制限・保存処理を引き継ぐ。
- [ ] ブラウザ内モデルの読み込み、生成、進捗、ベクトル保存を接続する。モデル処理をirisoutの解析対象からどう分離するか検証する。
- [ ] SSEのイベント形式、成功・失敗・完了、通信切断、画面破棄時の処理を定義する。完了通知なしの切断を成功扱いしない。
- [ ] 書き出しの実行確認、利用量の見積もり、新しい非公開プレイリストの作成を維持する。
- [ ] 書き出しの途中失敗では作成済みのプレイリストと進捗を示し、再送による重複作成を避ける。通信中断が実行済みの外部操作を取り消すとは扱わない。

完了条件: 両方の生成方式で進捗と保存結果を確認できる。書き出しは元のプレイリストを変更せず、処理中・完了・途中失敗を区別できる。外部APIへの書き込み試験には専用の対象を用いる。

### 5. 切り替えとirisoutへの還元

- [ ] 型検査・既存の業務処理試験・Hono経路試験・ブラウザ操作試験・本番ビルドを通す。
- [ ] 入力検証、認証、所有権確認、Cookieを使う更新要求の送信元検証を確認する。型共有は入力検証や認可の代わりにならない。
- [ ] 実データの複製で既存DBの読み書きを検証し、認証設定・起動手順・配信手順をREADMEへ反映する。
- [ ] 各機能の移植後にNext.js・Reactへの残存参照を調べ、不要になった依存と旧コードを削除する。
- [ ] 動作確認済みの旧版とDBの復元手順を残して切り替える。外部のYouTube操作はコードの切り戻しで復元されないことを記載する。
- [ ] アプリ固有の処理と共通化する接続処理を整理し、irisoutへ必要なものだけ提案する。

完了条件: 既存の対応機能が移植済みで、Bun上で本番起動でき、残る制約を記録している。Vercel等への公開は配信先の対応確認と別の公開作業として扱う。

## 今回の移植に含めないもの

要求ごとのサーバー描画、独自のサーバー関数構文、独自RPC、汎用キャッシュ自動更新、一般公開サービス化は含めない。現在未実装の「YouTubeへ遷移した後に次の動画を選択する」機能も同等移植の必須条件にはしない。モバイル表示の既知の問題は記録し、修正を含める場合は別の完了条件を置く。

## 計画・仕様・検証の記録先

この文書は作業順序を扱う。実装開始時にyt-util側へ移植の受入条件と進捗を置く。irisout本体の仕様変更が必要になった場合は、`docs/adr/`と`openspec/changes/`で設計・作業を定義し、`openspec/specs/`へ受入条件を反映する。制約の発見や段階完了は`STATUS.md`へ記録する。OpenSpecのCLIは`bunx @fission-ai/openspec`を使う。

依存導入・実行はBunを使う。irisout本体を変更した場合は`bun run check`、`bun run test`、`bun run build`、`bun run build:packages`、`bun run pack:smoke`と、変更に該当するブラウザ試験を行う。yt-utilの既存Bun試験は引き継ぎ、検証方式の統一だけを目的とする書き換えはしない。各段階の検証済み変更はJujutsuで説明を付けて履歴へ保存する。
