# ADR-0054: 共有Playgroundの公開範囲と投稿コード境界

- **状態**: 決定済み・内部実装済み（実運用未検証）
- **日付**: 2026-09-14

## コンテキスト

共有Playgroundは編集時点の単一JSXを保存し、保存後の内容をURLで読める利用例にする。
初回にアカウントや作品一覧を導入すると、認証、所有確認、削除、復旧の責務が増える。
また、Irisoutの`compile()`は初期HTML生成中に入力由来の処理を実行するため、投稿JSXを
サーバーで処理すると公式サイトの権限境界を越える。

## 決定

- 初回の共有範囲は限定公開とする。URLを知る利用者が閲覧できる状態であり、認証による
  秘密保持とは扱わない。
- 保存ごとに新しいIDを作り、既存IDの内容を更新しない。
- アカウントは導入しない。保存ごとに管理鍵を発行し、管理鍵による削除を提供する。
- 管理鍵を閲覧URLへ含めず、読取りページ、OGP、検索索引、ログへ出力しない。
- 投稿JSXは保存・閲覧・削除・OGP生成のどのサーバー経路でもコンパイル・実行しない。
  共有ページのSSRが描画するのは、運営側が管理する部品と保存済みのソース文字列である。
- 公開一覧、認証付き非公開、既存IDの上書き、編集履歴、投稿コードのサーバー実行は初回の
  対象外とする。

## 検討した代替案

- **投稿JSXをサーバーでSSRする**: 入力由来のコード実行と公式サイトの権限分離を同時に保証
  する必要があるため、初回は採用しない。
- **アカウントを導入する**: 所有確認と復旧は強くなるが、初回の保存利用例に必要な範囲を
  越えるため後段へ分ける。
- **既存IDを編集して更新する**: 共有済みURLの意味が変わり、再現性と削除の扱いが複雑に
  なるため採用しない。

## 結果

共有ページはSSRの利用例として、保存済みメタデータ、ソース全文、版、未実行表示を提供
できる。管理鍵を失った場合の自己削除不能、URL共有による閲覧可能性、既に取得されたコピーを
回収できないことを画面へ説明する。保存量、要求頻度、保持期間、バックアップの運用値は
公開前に別途確定する。
