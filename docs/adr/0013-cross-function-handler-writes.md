# ADR-0013: ハンドラからの関数越え書き込みの追跡

## ステータス

決定済み(change 未起票)

## コンテキスト

inline arrow ハンドラから動きゾーンの補助関数を呼ぶと
(`onClick={() => toggle(todo.id)}`)、`toggle` 本体の signal 書き込みが
解析されず `update_*()` が発火しない — **黙って更新が落ちる**(M2 以来の
挙動、change `dynamic-attribute-bindings` のテスト作成中に発見。ROADMAP
論点 0)。識別子参照ハンドラ(`onClick={toggle}`)は本体がそのまま
ハンドラ本体として解析されるので動く。引数を渡したいアイテム内ハンドラ
(`toggle(todo.id)`)で踏みやすく、「黙って落とすとバグの温床」の規約
(ADR-0004 の裏面)に反する。

前提となる現状の構造:

- `resolveHandlerBody`(`src/compiler/render.ts`)が inline arrow と
  識別子参照を同じ `HandlerBody` 形に正規化しており、解析経路はすでに
  1本。差は「呼び出しを追わない」ことだけ。
- 動きゾーンの function 宣言は出力に関数として存在しない。識別子参照
  ハンドラでも本体はマーカーごとの `__handler_<id>_<event>` として
  インライン展開される。

## 決定

### 1. 動きゾーン関数への呼び出しを追跡する(旧論点の選択肢 (b))

ハンドラ/action 本体内の呼び出し式で、callee が識別子かつ Babel の
binding 解決(`scope.getBinding`)で**動きゾーン(render() より後ろ)の
function 宣言と同一物**と確認できた場合、その関数を追跡対象とする:

- 呼び出し先本体をハンドラ本体と同じ規則で解析する(ADR-0009 の
  4文種制限・読み取り書き換え・書き込み代入化を同様に適用)。
- 呼び出し先の `writeDeclIds` を呼び出し元ハンドラへ合流し、`update_*()`
  の挿入位置は従来どおり**呼び出し元ハンドラ本体の末尾**とする(書き込みが
  全部終わってから更新、の現行セマンティクスを維持)。

### 2. 呼び出し先は出力に書き換え済み関数として1回だけ emit する

マクロ展開(呼び出し位置への本体インライン)はしない。呼び出し先の
書き換え済み本体をモジュールスコープの関数宣言として1回だけ出力し、
呼び出し式は authored のまま残す。引数の置換が不要で、複数箇所から
呼ばれても出力が肥大しない(ADR-0004: 膨らむ方向を避ける)。
emit するのは**追跡対象として実際に呼ばれた関数のみ**(未使用の
動きゾーン関数は従来どおり出力に含めない)。

### 3. 深さ制限は設けない(visited-set つき再帰)

呼び出し先の中の呼び出しも同じ規則で再帰的に追跡する。訪問済み Set で
相互再帰・自己再帰を打ち切る。「1階層のみ」の制限は、境界(2階層目)で
同じ「黙って落ちる」が一段ずれて再登場するだけなので採らない。

### 4. 追跡できない呼び出しの扱い

- **binding が解決できない**(`console.log` 等のグローバル): 従来どおり
  素通し。追跡対象の書き込みを含みようがないため誤検知はない。
- **binding は解決できるが動きゾーンの function 宣言でない**(仮引数・
  ハンドラ内ローカル宣言等を関数として呼ぶ場合): `scope limit` で拒否
  する。素通しすると同じ「黙って落ちる」穴が別の形で残るため。

## 検討した代替案

- **(a) 全拒否**(動きゾーン関数への呼び出しを scope limit にする):
  「黙って落とす」は塞げるが、追跡と無関係なユーティリティ呼び出しの
  誤検知判定に結局 binding 解決が要る。同じ解析コストを払うなら追跡まで
  やるほうが得。却下。
- **(c) 現状維持の明文化**(「書き込みはハンドラ本体に直接書く」を規約に
  明記するだけ): 黙って更新が落ちる挙動が残り、規約違反がコンパイル
  エラーにならない。ADR-0004 の「安全に拒否する」に反する。却下。
- **マクロ展開**(呼び出し位置に本体をインライン): 実引数→仮引数の置換
  機構が必要になり、複数箇所から呼ばれると本体が重複して出力が膨らむ。
  却下。
- **1階層のみ追跡**: 実装は最小だが、2階層目で同じ問題が再登場する。
  visited-set つき再帰との差分はごく小さい。却下。
