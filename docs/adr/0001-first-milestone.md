# ADR-0001: 最初のマイルストーンとアーキテクチャの初期選択

## ステータス

決定済み

## コンテキスト

CONCEPT.v2.md は irisout の思想（ビルド時実行 + 最小限の静的解析 + 依存グラフ → 専用コード生成）を定義しているが、
「最初に何を作るか」は未決定だった。以下の問いを詰めて決定した。

## 決定

### 1. 最初のマイルストーンのスコープ

**「式の依存解析」までを最初の動作確認ラインとする。**

対象:
- 単一コンポーネント、単一シグナル
- `{x + 2}` のような複数依存を含む JSX 式の依存抽出
- 依存グラフの構築
- 依存グラフから専用 `update_*` 関数へのコード生成

対象外（後続マイルストーン）:
- 複数コンポーネント間の props 伝播
- コンポーネント境界のインライン化（消去）
- 条件分岐・リスト等の構造的更新

理由: 単一シグナルの単一ノード更新だけでは「式の依存解析」という、このコンセプトの核心（静的解析の責務）を検証できない。複数依存の式まで含めることで、パイプライン全体（実行 → 静的解析 → 依存グラフ → codegen）を最小構成で通しつつ、本質的な難所を早期に検証する。

### 2. JSX/TSX の構文解析

**既存パーサの AST を利用する。自前パーサは書かない。**

理由: irisout の価値は codegen 側（依存グラフ → 専用更新コード）にあり、構文解析自体は独自性の対象ではない。Babel Parser や TypeScript Compiler API 等、JSX を AST に落とせる既存ツールを使う。

### 3. ビルド時実行におけるシグナル宣言

**専用ランタイム API（`signal()`, `derived()` 等）をコンポーネント関数内で呼び出す方式。**

理由: ビルド時に Node 上でコンポーネント定義を実際に実行し、その呼び出しを記録することでシグナル/派生値/props/ハンドラを発見する。独自構文・コンパイラマジック（`$state` 等のディコレータ）は静的変換ロジックを増やし初期スコープには重い。専用 API 呼び出しを実行時に記録する方式は実装が単純で、Solid/Svelte 等での実績もある。

### 4. JSX 式とシグナル実体の紐付け

**ノードID/ソース位置で式を一意に結びつける（変数名の文字列一致には頼らない）。**

理由: 変数名照合は変数名衝突・スコープの違いに弱い。各 JSX 式にソース位置ベースの一意な ID を付与し、静的解析で得た「自由変数名」と、ビルド時実行で登録された signal/derived の識別子を、コンポーネントスコープ内のバインディング情報を介して解決する。実装コストは変数名一致よりやや高いが、後続マイルストーン（複数コンポーネント、props）でも破綻しない基盤になる。

## 次のアクション

1. 単一ファイル・単一コンポーネント・単一シグナルの最小サンプルを1つ決める（例: カウンター）
2. Babel（または同等）で JSX を AST として取り出すパイプラインを組む
3. `signal()` / `derived()` ランタイム API を実装し、Node 上でコンポーネント関数を実行して登録情報を得る
4. JSX 式ノードにソース位置ベースの ID を振り、自由変数の依存を静的抽出する
5. 実行で得た signal/derived の情報と、静的解析で得た式の依存情報をノードID経由でマージし、依存グラフを構築する
6. 依存グラフから `update_*` 関数を生成する
