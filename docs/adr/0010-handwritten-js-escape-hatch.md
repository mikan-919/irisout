# ADR-0010: 手書きJSとの共存単位を`<Escape>`(JSX要素単位)にする

## ステータス

**棚上げ**(2026-07-14。決定済み・未実装のまま実装を見送り)。
ADR-0011(`use=`)の決定により、本ADRの主要ユースケース(手書きJS・
レガシーwidgetの統合)は「実要素+`use=`アクション本体からのグローバル
委譲」で書けるため、専用マーカー要素は作らない。詳細は末尾
「棚上げの経緯(2026-07-14)」を参照。再起票のトリガーは
「インラインの不透明本体の実需」(同節参照)。設計決定の経緯は
change `escape-hatch-design`(アーカイブ済み)に残る。

## コンテキスト

irisoutのコンパイラは、受理しないパターンに当たると`compile:`+
`(scope limit)`エラーで拒否する(ADR-0004: ソースが要求する以上の
実行を生成しない、その裏面としての「安全に拒否する」)。この設計
自体は正しいが、現状は1つの`scope limit`がコンポーネント全体の
コンパイルを止める。アプリが少しでもコンパイラのカバー範囲外の
パターンを必要とすると、コンパイラが完成するまでアプリ全体が書けない。
手書きvanilla JSとの共存を認める公式な逃げ道がまだ無いため、
パリティの薄い箇所に当たった時点でプロジェクト全体が詰む
(ROADMAP.md「3. エスケープハッチ」、2026-07-14相談)。

ADR-0008は、authoring APIを「変数ゾーン→UIゾーン→動きゾーン」の
3構造(constのみ/render()マーカー/function宣言)に固定し、ハンドラは
動きゾーンのfunction宣言へJSX側から識別子参照する形をとる、という
前例を確立した。この配線パターン(識別子参照+巻き上げfunction宣言)は
「型・rename・go-to-defが効く」という理由でハンドラ配線に採用された
経緯があり、escape hatchの配線にもそのまま転用できる。

## 決定

### 1. 共存の単位: JSX要素1つ

検討した3つの単位と却下/採用理由:

| 単位 | 影響範囲 | 却下/採用理由 |
|---|---|---|
| (a) コンポーネント全体 | そのコンポーネントは丸ごとirisout管理外 | コンパイラのカバー範囲が1箇所広がるたびの効果が薄い。「1パターンがページ全体を止める」問題を「1パターンがコンポーネント全体を止める」に縮小するだけで、M5のUNRESOLVED(06)/(07)のような「アイテム内の一部だけ手書きにしたい」ケースを解決できない。却下 |
| (b) 新しい専用ゾーン(「手書きゾーン」) | ゾーン構造に第4のゾーンを追加 | ゾーンはコンポーネント直下の構造を表すもので、「UI木の特定の1箇所」という局所的な話とは粒度が違う。UI木の途中に手書き部分を挟みたいケースを表現できない。却下 |
| (c) JSX要素1つ | UI木の任意の位置に置ける | ブラスト半径が最小。1箇所の未対応パターンだけをピンポイントで手書きに逃がせ、他の部分はirisoutの管理下に留められる。ADR-0008の「識別子参照+巻き上げfunction宣言」パターンをそのまま転用できる。採用 |

### 2. 記法: `<Escape mount={identifier} />`

ADR-0008のハンドラ配線と同型の配線にする:

```jsx
render(
  <div class="widget">
    <Escape mount={setupLegacyWidget} />
  </div>
)

function setupLegacyWidget(container) {
  // container は<Escape>の位置に生成されたDOM要素(コンパイラは
  // この中身を一切解釈しない)。ここから先は手書きvanilla JS。
  container.textContent = '...'
  container.addEventListener('click', () => { /* ... */ })
}
```

- `<Escape mount={identifier} />`はコンパイラが特別扱いする組み込み
  マーカー要素(`render`/`signal`と同様、ビルド時に消えるイディオム)。
- `mount`属性は、ハンドラと同じ「`render()`より後ろのfunction宣言への
  識別子参照」ルールに従う(ADR-0008の識別子参照ルールの再利用)。
  それ以外の形式(inline arrow、`render()`より前の宣言への参照など)は
  compile errorで拒否する。
- コンパイラは`<Escape>`の位置に空のコンテナDOM要素を1つ生成し、
  マウント時に`mount(container)`を1回呼び出すコードを生成する。それ以外の
  解釈は一切行わない(中身のJSX/式は書けない — `<Escape>`は常に
  自己完結タグで、子要素を持てない)。
- `mount`が参照する関数の期待シグネチャは`(container: HTMLElement) => void`。
  `Escape`自体の型の出所は`render`/`signal`と同じイディオム(現状は素の
  識別子)に従う。エディタで型を効かせる型定義の置き場所は実装changeで
  決める。

### 3. teardownは今回作らない(グローバル副作用のリークは受け入れたリスク)

ADR-0004の「使われていない機構は作らない」に従い、明示的な`unmount`
コールバックは今回の設計に含めない。ただし根拠はADR-0005決定4
(アイテムteardown不要)の単純な転用では**ない**。ADR-0005は「factory関数が
登録するのはインスタンス自身のDOM部分木に閉じたものだけ(外部リソースへの
登録は一切ない)」をコンパイラが生成するコードの性質として保証できたが、
`mount`本体は不透明な任意コードであり、この保証は成立しない。

- コンテナDOM部分木に閉じた状態・リスナーは、keyed reuseやリスト削除で
  `remove()`された際にDOM部分木ごとGC対象になる(ADR-0005と同じ)。
- 一方、`document`/`window`へのリスナー登録、`setInterval`、Observer、
  外部接続などのグローバル副作用は、コンテナ削除後もリークする。これは
  **受け入れたリスク**とする。
- 将来実害が出た場合は、`mount`の返り値をcleanup関数として呼ぶ形
  (React `useEffect`と同型)で後方互換に追加できる(未決定事項参照)。

### 4. リストアイテム/条件分岐ブランチ内での使用

`<Escape>`はリストアイテム・条件分岐ブランチのfactory関数内にも置ける
(M5実装後)。この場合、`mount`はそのインスタンスごとに1回呼ばれる。
これはM5のUNRESOLVED(06)/(07)(ネストした構造ユニット)に対する、
コンパイラ側の一般化された対応を待たずに使える暫定的な逃げ道になり
うるが、本ADRではその活用方法の確定までは踏み込まない(M5側の
follow-up changeで判断する)。

### 5. mount関数本体はコンポーネント内の他の宣言に触れられない(compile errorで拒否)

Non-Goal(signal/derivedとの同期はしない)を強制する。mount関数の本体は
不透明(解析しない)だが、生成コードではsignal/derivedはプレーン変数になり、
動きゾーンの他のfunction宣言や変数ゾーンのプレーンconstも、生成コード上の
置き場所・形がauthored codeと一致する保証がない。本体がそれらへの参照を
含むと、実行時にReferenceError/TypeErrorで静かに壊れる。

ADR-0007と同じ「安全に拒否」に従い、コンパイラはmount関数本体に識別子
スキャンを行い、参照可能な識別子を**mount自身の引数・ローカル宣言・
モジュールimport・グローバル**に限定する。コンポーネント内の他の宣言
(追跡宣言・プレーンconst・他のfunction宣言)への参照を見つけたら
compile error(scope limit)で拒否する。追跡宣言に限定せず全宣言を拒否する
理由は推移的参照の遮断 — 「mountが呼ぶhelperがsignalを読む」経路は、
helper自体がコンポーネント内宣言なので直接拒否される。スキャンはスコープ
解析を伴わない保守的なものでよい(mountローカルがコンポーネント内宣言と
同名の場合の誤検知は許容する)。

状態と連動する振る舞いが必要な場合は`use=`(change `action-use-attribute`)を
使う。

### 6. `use=`(element-use-action)との役割分担

`<Escape mount>`と`use=`は同じ配線(識別子参照+要素を引数に受ける関数)の
2変種で、区別は1軸: **本体をコンパイラが解析するか**。`use=`は解析
される(signal読み書き可、返り値クロージャがリアクティブ配線される)、
`<Escape>`は不透明(コンポーネント内の宣言に触れられない)。一言で言えば「`use=`は
irisoutの世界の中で要素に振る舞いを足す。`<Escape>`はirisoutの世界の
外に出る」。この1軸は両方のADR(本ADRとchange `action-use-attribute`が
起票する予定のADR)に明記する。

## この決定がこれまでの判断とどう整合するか

- ADR-0004(統治原則): `<Escape>`はコンパイラの管理範囲を明示的に縮小
  するもので、生成コードが「ソースが要求する以上の実行をしない」原則
  そのものには反しない — mount呼び出し1回だけを生成し、それ以上は
  何も足さない。teardownを作らない判断(決定3)もこの原則の適用。
- ADR-0005(factory-per-unitクロージャ): teardown不要の判断を踏襲する
  (決定3)。ただし根拠は部分的な再利用にとどまる — ADR-0005が保証した
  「外部リソース登録なし」は不透明なmount本体には成立せず、グローバル
  副作用のリークを受け入れたリスクとして明記した。
- ADR-0008(ゾーン構造): `mount`属性の識別子参照ルール(決定2)は
  ADR-0008のハンドラ配線ルールの転用。`<Escape>`は新しいゾーンを
  追加するものではなく、既存のUIゾーンの中に置ける1つのマーカー要素
  として扱う。
- ADR-0007(安全に拒否): コンポーネント内宣言参照の拒否(決定5)は
  「検証できないものは静かに通さない」という同じ方針。

## 未決定事項(後続で詰める)

- `<Escape>`という名前が最終的な採用名かは、実装着手時に再検討する
  (例: `<Raw>`、`<Handwritten>`等の代替名)。
- M5のUNRESOLVED(06)/(07)を`<Escape>`で暫定的に迂回する運用を正式に
  推奨するかどうかは、M5側のfollow-up changeで判断する(決定4)。
- **コンテナ要素のタグ名**。「空のコンテナDOM要素」のタグが未規定。
  divは`<ul>`/`<tbody>`/`<select>`内で不正HTMLになり、`nth-child`系の
  CSSセレクタも壊す。タグ指定手段(例: `<Escape tag="li" mount={...} />`)の
  要否を実装changeで決める。
- **mount呼び出しのタイミング**(コンテナがdocumentに接続される前か後か)。
  手書きwidgetはsetupでレイアウト測定(`offsetWidth`等)を行いがちで、
  接続前の呼び出しだと0を返す。実装changeで決める。
- **明示的cleanupの追加**(`mount`の返り値をcleanup関数として呼ぶ、
  React `useEffect`と同型)。グローバル副作用のリーク(決定3)が実害に
  なったら後方互換で追加する。

## 実装への引き継ぎメモ

(棚上げにより無効。再起票時は下記「棚上げの経緯」の再検討事項も
あわせて読むこと。)

本ADRおよびchange `escape-hatch-design`は設計決定のみを対象とし、
`src/`は変更しない。実装は本ADRに基づく別changeで行う。影響範囲は
以下の2箇所:

- `src/compiler/render.ts`: JSX要素解析に`<Escape mount={...} />`の
  特別扱い(組み込みマーカーとしての認識、子要素禁止の検証、`mount`属性の
  識別子参照解決、本体の識別子スキャンによるコンポーネント内宣言参照の
  拒否)を追加する。
- `src/codegen.ts`: `<Escape>`の位置へのコンテナDOM要素生成と、
  マウント時の`mount(container)`呼び出しコード生成を追加する。

## 棚上げの経緯(2026-07-14)

実装change起票の直後、「ルート要素に`use=`すれば要素は全部取得できるの
だから専用要素は要らないのでは」という指摘(2026-07-14相談)を受けて
再検討し、実装を見送った。

- `use=`本体はADR-0009の解析(4文種制限)を受けるため「任意のJSを
  インラインで書ける」わけではない — 不透明本体はEscapeだけの性質、
  という1軸の区別(決定6)自体は正しいまま。
- しかし主要ユースケース(レガシーwidget統合)は、`use=`アクション本体
  からコンパイル管理外のグローバル関数へ委譲する式文1つ
  (`window.LegacyLib.init(el)`)で書ける。**これを公式な逃げ道と
  位置付ける。**
- コンテナ問題(タグ名・属性・スタイルの指定、未決定事項に残っていた)は
  実要素+`use=`では構造的に発生しない。`<Escape tag=...>`案は実要素の
  劣化コピーだった。
- scope limit苦情の受け皿はADR-0011決定7のtriage手続きが既に定義して
  いる。「1パターンで全体が詰む」への制度的な答えはEscapeなしで回る。
- ROADMAPの「使ってもらえる閾値」はM5+エスケープハッチからM5+`use=`へ
  置き直した。spec `handwritten-js-escape-hatch`は削除(git履歴と
  `openspec/changes/archive/2026-07-14-escape-hatch-design/`に残る)。

**再起票のトリガー**: インラインの不透明本体の実需 — グローバル委譲では
書けない/書きたくないケース(委譲先を別ファイル・script-tagに置くこと
自体が苦痛になる規模の手書き部分)がフィクスチャに現れた時点。その際は
専用マーカー要素ではなく「実要素への不透明属性」(`<li escape={fn}>`の
ような形 — コンテナ問題を持たない)を第一候補として再設計する。
