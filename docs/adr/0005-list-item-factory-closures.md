# ADR-0005: リストアイテム/条件分岐のレンダリングをfactory-per-unitクロージャに変更

## ステータス

決定済み(設計方針。実装は未着手 ― 後続の実装計画で扱う)

## コンテキスト

ADR-0002はリストアイテム・条件分岐ブランチ内のイベントハンドラをスコープ制限として先送りにした。理由は、両者とも更新のたびに`innerHTML`で中身を丸ごと再生成しており、貼り付けた`addEventListener`が消えてしまうため。ADR-0002の未決定事項は「コンテナレベルのイベント委任」を次の一手として示唆していたが、検討の結果、委任だけでは解決しない別の制約があることが分かった: 今のリストアイテムは`renderItemTemplate`(`src/classify.js`)がテキスト/式の子要素しか許さず、アイテムごとの永続的な状態を一切持てない ― `classify.js`のコメント通り、アイテムのフィールドは追跡対象の宣言ではなくコールバック引数由来で、登録するdeclIdが存在しない。イベント委任はハンドラの配線は解決するが、「アイテムごとの状態がない」という制約には効かない。

Web Components(Custom Elements)による解決も検討したが、却下した。

- **Customized built-in element**(`<li is="todo-item">`)はSafariが一切実装していない。
- **Autonomous custom element** + `display: contents`はペイント(レイアウト)は透明にできるが、DOMツリー構造そのものは変わらないため、ラッパー要素(`<todo-item><li>...</li></todo-item>`)を挟むと`ul > li`のようなCSS子結合子や`:nth-child`によるゼブラストライプが壊れる。

いずれもCONCEPT.v2.mdの「熟練開発者が手で書くなら」という基準、およびADR-0004の統治原則(ソースが要求していない副作用を生まない)に反する。

## 決定

### 1. スタンプ機構: `<template>` + `content.cloneNode(true)`

文字列HTML(`insertAfter`/`createContextualFragment`、現行の`htmlToNode`)に代えて、リストアイテム・条件分岐の中身は`<template>`要素として1回だけ生成し、インスタンスごとに`cloneNode(true)`で複製する。ラッパー要素は挟まない ― クローンした実要素(例: `<li>`)がそのまま親(`<ul>`)の直接の子になる。

### 2. アイテム/ブランチごとに1つの生成された「factory関数」

リストアイテムテンプレート・条件分岐の各ブランチは、既存の`__itemInner_${id}`/`__itemHtml_${id}`(現在は文字列スタンプ専用、`src/codegen.js:23-29`)を拡張し、以下を1つの関数にまとめて生成する:

- `<template>`のクローンとマーカー要素の取得
- そのインスタンス固有の状態を保持する素のローカル変数(例: `let editing = false;`)。`signal()`ラッパーは使わない ― 生成された関数呼び出し自体が既にクロージャ境界を提供するため、追加のラッパーは不要。
- そのインスタンスの`update_*`関数(ローカル変数を閉じ込めて参照)
- そのインスタンスのイベントハンドラ登録(直接`addEventListener`。委任は不要 ― アイテムは再生成時に破棄されなくなるため、一度貼ったリスナーは残る)

### 3. リスト更新はkeyed reuseへ変更

`update_<list>()`は、現行の「keyが既存なら`innerHTML`で中身だけ差し替え、なければ新規HTML文字列から生成」(`src/codegen.js`の該当ロジック)を、「keyが既存ならfactory関数が返したハンドル(要素+状態への参照)をそのまま使い回し、なければfactory関数を新規呼び出し」に変更する。これによりアイテムの生存期間中、ローカル状態とイベントリスナーは保持され続ける。

### 4. 削除時の明示的teardownは現時点では作らない

factory関数が生成する状態・リスナーは、そのインスタンス自身のDOM部分木の中だけに閉じている(外部リソースへの登録は一切ない)。keyed Mapから参照を落とし、DOM要素を`remove()`すれば、状態・リスナー・DOM部分木は一括してGC対象になる。`onLeave`的な明示的teardown呼び出しは、将来アイテムが外部リソース(タイマー、購読等)を持つ機能ができるまでは不要(ADR-0004: 使われないものは作らない)。

### 5. 生成出力からの`signal()`除去は、この決定の対象外

アイテムごとのローカル状態は最初から素の変数として生成するため、リストアイテムに関して`signal()`除去の問題はそもそも発生しない。トップレベルコンポーネントの`signal()`除去(単一式範囲内での書き換え)は別途、ADR-0004の未決定事項として扱う。

## スコープ制限(この回で対応しないこと)

- リストアイテム内に**さらにネストした構造ユニット**(アイテムの中に条件分岐やリストがある場合)を持つケース。まずは1階層のみ。
- Web Components化は完全に却下 ― 再検討する場合は、Safari互換性とDOMツリー透明性という2つの具体的な破綻が解消されない限り再浮上させないこと。

## 未決定事項(後続で詰める)

- ネストした構造ユニット(リストの中の条件分岐、条件分岐の中のリスト等)への同じfactoryパターンの適用。
- `signal()`/`derived()`をトップレベルコンポーネントの生成出力からも除去する、単一式範囲内での書き換え(ADR-0004参照)。
