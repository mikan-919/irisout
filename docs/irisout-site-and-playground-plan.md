# Irisout公式サイトと共有Playgroundの計画

作成・更新日: 2026-09-14。検討中の計画であり、実装済みの仕様ではない。本書の選択と数値は実装を分割するための提案とする。実装着手時に設計判断を`docs/adr/`へ、受入条件を`openspec/specs/`と対応する`openspec/changes/`へ反映する。

## 1. 目的と初回公開の範囲

公式サイトで、Irisoutの仕組み、導入方法、API、例、対応範囲を読めるようにする。文書は検索エンジン、直接URL、JavaScriptを無効にしたブラウザから閲覧できることを条件とする。

Playgroundでは、単一ファイルのJSXを編集・実行し、保存時点のソースをURLで共有する。保存後に作られたIDのページを要求ごとに生成し、IrisoutのSSR（サーバーが要求ごとのデータからHTMLを生成する処理）の利用例にする。この利用例に必要な範囲で、要求データからHTMLとブラウザへの引継ぎデータを生成するサーバー用入口をIrisoutへ追加する。ブラウザ内コンパイルとSSRは別の課題として検証する。

| 区分       | 初回公開に含めるもの                                                                  | 後続の段階へ分けるもの                                        |
| ---------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 公式サイト | トップ、文書一覧・詳細、見出し検索、公式例への導線                                    | 多言語化、文書の版別配信、全文検索サービス                    |
| 編集・実行 | 単一`.jsx`、テキスト入力、実行・停止、診断、結果表示、ソース書き出し                  | 複数ファイル、任意のnpm依存、補完付きエディタ、自動実行       |
| 保存・共有 | 限定公開、保存ごとの新規ID、削除用の管理鍵、共有ページのSSR                           | 公開一覧、認証付き非公開、既存IDの上書き、編集履歴            |
| 描画       | 文書のSSG、Irisoutのサーバー用入口、共有ページ一種類の要求ごとのSSRと初期状態の引継ぎ | 汎用ルーター、ストリーミングSSR、サーバー上での投稿コード実行 |

限定公開は「URLを知る人が閲覧できる」状態であり、認証による秘密保持ではない。公開・非公開は第6段階で扱う。初回公開でも削除とリンク無効化を提供し、保存だけを先に一般公開しない。

## 3. URL・配置・配信

| URL                         | 応答              | 内容・条件                                                 |
| --------------------------- | ----------------- | ---------------------------------------------------------- |
| `/`                         | SSG、200          | 既存トップを使用。文書とPlaygroundへリンクする             |
| `/docs`                     | SSG、200          | 分類別一覧、導入入口、見出し検索                           |
| `/docs/:slug`               | SSG、200または404 | 本文、目次、前後リンク、対象のIrisout版                    |
| `/playground`               | SSG、200          | 新規編集画面。初期例はリポジトリで管理する                 |
| `/playground?example=:slug` | 同じ静的画面      | 登録済み公式例だけを選択する。値をファイルパスに変換しない |
| `/playground/:id`           | SSR、200または404 | 保存時のタイトル、説明、ソース全文、版、未実行表示         |
| `/api/playgrounds`          | POST              | 新規保存。第5節の形式を受け付ける                          |
| `/api/playgrounds/:id`      | DELETE            | 管理鍵を検証して削除する                                   |

末尾スラッシュなしを正規URLとし、別表記は308で転送する。存在しない文書や共有IDをトップのHTMLへ転送しない。開発時も本番時も、URLの直接入力と再読込みで同じページまたは404が返ることを確認する。

配置案は次を基準にし、未使用のディレクトリは先に作らない。

| 配置                                      | 責務                                                  |
| ----------------------------------------- | ----------------------------------------------------- |
| `app/web/src/`                            | 画面、文書レイアウト、編集操作、隔離環境との通信      |
| `app/web/content/docs/`                   | 公開文書のMarkdownと必要な画像                        |
| `app/web/content/examples/`               | 実行可能な公式例と識別用の一覧                        |
| `app/web/scripts/`                        | 文書生成、リンク・例・配信物の検査                    |
| `app/web/server/`                         | 共有ページ、保存・削除API、保存先との接続             |
| `app/web/test/`                           | サイトの試験。ルート設定へ収集対象を追加する          |
| `packages/compiler/`、`packages/runtime/` | ブラウザ用コンパイラ境界、SSR契約に必要な本体変更のみ |

配信は、静的ファイルと共有ページ・APIを扱うBunサーバー一つ、永続ディスク上のSQLite一つを初期案とする。データベースはビルド出力の外へ置く。配信先が永続ディスクを提供しない場合は第4段階の着手前に保存方式を決め直す。複数の保存基盤を差し替える抽象層は先に作らない。

投稿コード用の隔離配信元は公式サイトと分ける。同じサーバーを使う場合も、配信元ごとの経路と応答ヘッダーを分け、隔離側へ保存APIや管理用データを提供しない。配信元の具体的なドメイン名とヘッダーは第2段階で検証する。

## 4. 文書の入力とSSG

### 入力の契約

公開本文はMarkdownを正本とし、JSX内への本文の二重記載を避ける。既存の[導入文書](./getting-started.md)から移す内容は、公開側へ移動して元の入口を案内にするか、同じ入力を参照して生成する。コピー後に二つを別々に保守しない。内部設計文書は公開用の操作説明と分け、必要な箇所へリンクする。

初期の掲載順は「導入」「状態と更新」「イベント」「条件分岐と一覧」「部品とファイル分割」「ライフサイクル」「API」「診断と対応範囲」とする。トップのCounter・List・SVGに対応する実行例を置く。

- 冒頭メタデータ（front matter）は`title`、`description`、`slug`、`section`、`order`を必須とする。`slug`は英小文字・数字・ハイフンの一階層とし、重複・未知の分類・分類内の順序重複をビルドエラーにする。
- ページ名はメタデータから一つの`h1`として生成する。本文は`h2`から始め、目次は`h2`・`h3`を対象とする。日本語や同名見出しのID生成規則を固定し、リンク検査も同じ規則を使う。
- コードブロックの言語は使用するものだけを許可する。実行例への参照は一覧に登録した識別子で指定し、同じソースから表示用コードとPlaygroundの入力を得る。
- Markdown内の任意HTML、MDX、スクリプト実行は初期範囲に含めない。サイト内リンク、相対文書リンク、見出しリンク、画像参照を生成先URLへ解決し、参照切れを失敗にする。
- 外部リンクは許可するURL形式を検査する。外部サイトの生存確認は通常のビルド成功条件にしない。掲載する版はサイト全体の設定で固定し、例の検査に用いる版と一致させる。

### 生成とブラウザへの配信

ビルドは「メタデータ検査 → Markdown解析 → コード強調表示 → 本文・目次・前後リンク生成 → リンク検査 → HTML・検索索引出力」の順に進める。HTMLには`title`、説明、正規URL、OGP（共有サービス向けのページ情報）を含める。サイトマップにはトップと公開文書だけを含め、共有コードは含めない。

文書本文はIrisoutが更新するDOM領域の外へ置き、静的レイアウトへ合成する案から検証する。Irisout側は必要な操作部を生成する。生成済みの動的領域へ本文を後から挿入する方法は、初期HTMLと更新先の対応を壊すため採らない。文書ごとの本文生成をコンパイラの新機能にしない。

検索はタイトルと見出しの文字列検索から始める。ビルド時のJSON索引を検索操作時に読み込み、本文のMarkdown解析器は読み込まない。テーマはCSSの配色設定を既定にし、切替操作、コードのコピー、目次の追従だけを追加する。モバイルの文書一覧は標準HTMLでも開閉できる構造にし、JavaScriptなしでも到達できるようにする。

文書だけを開いたときにPlaygroundのコンパイラを取得しない。配信物の依存一覧とブラウザの通信を確認し、Markdown解析器・強調表示器はどのブラウザ向け生成物にも、コンパイラは文書向け生成物にも含めない。

## 5. 共有データ・権限・HTTPの契約

### 保存する値

保存対象は編集時点のスナップショットとする。既存IDの内容は更新しない。共有ページを編集して保存した場合も新規IDを返し、元のURLの内容を変えない。入力ミスやコンパイルエラーを含むソースも保存できる。

| 項目                          | 提案する制約・用途                                                        |
| ----------------------------- | ------------------------------------------------------------------------- |
| `schemaVersion`               | 初期値1。未知の版は422で拒否する                                          |
| `id`                          | サーバーで128ビット以上の乱数から生成。URLで使える形式を固定する          |
| `title`                       | 必須。前後の空白除去後1〜120 Unicodeコードポイント                        |
| `description`                 | 任意。最大1,000コードポイント。HTML・Markdownとして解釈しない             |
| `source`                      | 単一JSX、UTF-8で最大64 KiB。改行を含め、保存時に内容を改変しない          |
| `compilerVersion`             | 配信側で利用可能な版の一覧から選ぶ。任意のURLやパッケージ名は受け付けない |
| `visibility`                  | 初期は`unlisted`のみ。未知の値・`public`・`private`は422                  |
| `createdAt`                   | サーバーのUTC時刻                                                         |
| `deletedAt`                   | 未削除はnull。削除の確認と再送処理に使う                                  |
| `deleteTokenHash`             | 管理鍵のハッシュ。HTML・読取りデータ・ログへ含めない                      |
| `requestId`、保存要求の照合値 | 保存再送を識別する。管理鍵と入力の一致を検証する                          |

POSTの本文は`schemaVersion`、`title`、`description`、`source`、`compilerVersion`、`visibility`、`requestId`だけを受け付ける。ID・日時・削除状態・ハッシュはサーバーが設定し、送信者による指定を拒否する。`requestId`はブラウザが暗号学的乱数で生成するUUIDとし、データベースの一意制約とトランザクションで同時再送も一件にまとめる。

受信本文全体の上限は128 KiBとし、読み込みながら上限を確認する。`Content-Length`の有無に依存しない。文字数とバイト数の違いを日本語入力で検査する。未知の項目、型違い、不正なIDを拒否する。診断、生成JavaScript、生成HTML、プレビュー画像は初期の保存対象に含めない。

### 管理鍵と保存の再送

アカウントを導入せず、共有ごとに256ビット以上の暗号学的乱数による管理鍵をブラウザで生成する案を使う。管理鍵は削除権限そのものであり、閲覧URLには含めない。保存・削除要求は`Authorization`ヘッダーで管理鍵を送り、サーバーはハッシュだけを保持する。

ブラウザは送信前に`requestId`、管理鍵、送信する入力を下書きと関連付けて公式サイト側のブラウザ保存領域へ保持する。保存できない環境では同じ情報を書き出してから送信する。同じ`requestId`・管理鍵・入力の再送は同じIDを返し、異なる入力の再送は409とする。これにより応答が失われても、同じ要求を再送して保存結果を確認できる。削除済みの要求を正しい管理鍵で再送した場合は410とし、復活させない。管理鍵が異なる再送は404とする。

保存完了画面では「共有URL」と「削除用の管理鍵」を別の操作で取得できるようにする。管理鍵を失うと自己操作では削除できないこと、ソースに秘密情報を含めないことを保存前に示す。管理鍵は初期HTML、OGP、検索索引、隔離環境、解析ログへ送らない。

### 応答と削除

| 操作・失敗                         | 応答と画面の扱い                                                |
| ---------------------------------- | --------------------------------------------------------------- |
| 新規保存／同一要求の再送           | 201／200。ID、共有URL、作成日時を返す。管理鍵は応答に反射しない |
| 不正JSON／非対応の送信形式         | 400／415。入力はブラウザに残す                                  |
| 上限超過／項目・版の不一致         | 413／422。対象項目を示す                                        |
| 保存要求IDの競合                   | 409。新規保存と再送を混同しない                                 |
| 要求頻度の超過                     | 429と`Retry-After`。入力を失わず再試行できる                    |
| 未存在・形式不正・削除済みの共有ID | ページは404。削除済みのタイトル・ソースを応答へ残さない         |
| 削除権限がない                     | DELETEは404。管理鍵の正誤や記録の存在を追加で漏らさない         |
| 管理鍵による削除／同じ削除の再送   | 204。既に削除済みでも成功として扱う                             |
| 保存先の停止                       | 503。共有ページでは障害表示。404や保存成功に置き換えない        |

削除処理は、閲覧不能化とタイトル・ソース・説明の消去を同じトランザクションで行う。再送の識別に必要な記録だけを残す。共有HTMLとAPI応答には`Cache-Control: no-store`を付け、初期段階では共有ページのキャッシュを設けない。既に取得されたコピーや外部サービスの表示までは回収できないことを削除画面に示す。

限定公開ページは`noindex`、`Referrer-Policy: no-referrer`とし、サイト内検索・サイトマップから除外する。OGPは保存時のタイトル・説明と共通画像だけを使い、ソースを説明へ転用しない。URLを共有サービスへ渡すとそのサービスも内容を取得し得ることを共有操作で説明する。

書込みAPIは公式サイトの`Origin`を検査し、POSTはJSON形式だけを受け付ける。DELETEの本文は不要とする。また、他の配信元へ書込み用CORSを許可しない。頻度制限の初期案は送信元ごとに保存10回/分・100回/日、削除試行30回/分とする。これは認証の代替ではない。配信先のプロキシから信頼する送信元情報、記録保持期間、全体の保存量上限を第4段階で固定する。

## 6. ブラウザ内コンパイルと実行の境界

### ブラウザ用入口

単一ソースのコンパイル処理を、ファイル読込みを伴う`compileProject()`から分離する。ブラウザ側へNodeのファイル機能の代替実装を持ち込まない。公開入口を追加する場合はADRとOpenSpecを先に作り、既存の`compile()`・`compileProject()`の結果と診断を維持する。

初期対応は単一`.jsx`、同一ファイルの部品、Irisoutが既に受け付ける記法に限る。静的import、動的import、外部モジュール、外部資源の読込みはPlaygroundの対象外とする。これはIrisout本体の対応範囲とは分けて表示する。構文の拒否だけを隔離の根拠にしない。

コンパイラと実行時処理は同じ版を固定して配信する。共有ページを開いても自動で新版へ移さない。保存された版を配信できない場合、ソースの閲覧・書き出しは維持し、「現在の版で複製して実行」を明示的な操作にする。旧版資産を停止する条件と保存期間は第5段階の公開判断で決める。

### 隔離環境

投稿ソースはコンパイル時にもコードとして動く。そのため、公式サイトの画面や同じ配信元のWorkerへ直接渡して実行しない。案は「公式サイト → 別配信元の実行管理iframe → コンパイル用Workerと結果用iframe」とする。Workerは画面処理と別の実行単位であり、権限分離や通信禁止を自動で提供するものではない。

- 実行管理iframeには公式サイトのCookie、管理鍵、保存APIへの権限を持たせない。親から渡すものはソース、コンパイラ版、実行番号だけにする。
- コンパイル用Workerは実行ごとに作成し、成功・失敗・取消しで破棄する。時間上限の初期値は5秒とする。結果の合計サイズは1 MiBまでとし、上限超過を診断として返す。
- 結果用iframeは`sandbox="allow-scripts"`を基本とし、`allow-same-origin`、フォーム送信、上位画面への遷移、ポップアップ、ダウンロードを許可しない。生成HTML・JavaScriptはこの中でだけ扱う。
- CSP（読み込める資源と実行方式を制限する応答方針）は公式サイト・実行管理画面・Worker・結果画面で個別に定義する。`new Function()`に必要な許可はコンパイル側だけに置く。外部通信、任意の追加スクリプト、入れ子の画面を既定で拒否し、必要な固定資産と生成コードの読込みだけを許可する。
- `postMessage`等の受信は送信元ウィンドウ、可能な場合は配信元、メッセージ形式、サイズ、実行番号を検査する。送信元が`null`になる隔離画面では`null`だけを識別根拠にしない。受信データから親画面でコード実行やHTML挿入をしない。

iframeの権限指定は[MDNのsandboxの説明](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox)を、WorkerへのCSP適用は[MDNのWorkerとCSPの説明](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers#content_security_policy)を参照する。Workerは通常、作成元の文書とは別のCSPが適用されるため、配信するWorker自身の応答も検査する。

隔離構成は第2段階の試作で成立を確認してから確定する。iframeだけでCPU・メモリの上限や外部通信の完全な封鎖を保証できるとは扱わない。無限ループからの復旧、結果画面自身の遷移、外部通信の試行を試験に含め、残る制約を画面と運用資料へ記録する。操作不能を解消できない構成のまま一般公開へ進めない。

### 編集・実行の状態

共有ページはコードと説明を読める状態で開き、実行は利用者がボタンを押して始める。入力中の自動コンパイルも初期範囲に含めない。コンパイル自体が投稿コードの実行を伴うため、診断取得のための自動処理もしない。

| 状態                   | 表示・操作                                                 |
| ---------------------- | ---------------------------------------------------------- |
| 未実行                 | ソース全文、版、「未実行」。実行・保存・書き出しが可能     |
| コンパイル中           | 進行表示と停止。入力・書き出しは継続可能                   |
| 実行中・成功           | 当該ソースの結果と停止。結果がどの実行番号のものか保持する |
| ソース編集後           | 前の結果に「変更前の結果」と表示する                       |
| 構文・対応範囲エラー   | 行・列・メッセージをテキスト表示。編集内容を維持する       |
| 実行時エラー・時間超過 | コンパイル診断と区別して表示。停止・再実行で復旧する       |
| 保存失敗・通信断       | 編集と書き出しを維持する。同じ保存要求を再送できる         |

停止と再実行では旧Worker・結果画面を破棄し、旧実行番号の結果は反映しない。診断や例外の文字列は信用せず、HTMLとして挿入しない。診断は「今回のブラウザでの結果」として扱い、共有ページのサーバー側で保証された結果とは表示しない。

## 7. Irisoutのサーバー用入口と共有ページのSSR契約

### 追加するIrisoutの境界

公開単位は[ADR-0047](./adr/0047-single-public-package.md)に従って`irisout`一つを維持し、別のnpmパッケージは作らない。サーバー用の副入口は`irisout/ssr`を候補とし、公開APIの名前は第2段階の試作後にADRとOpenSpecで確定する。

入口は、運営側が管理する部品をビルド時に処理し、要求時には直列化できる入力からHTMLとブラウザへの引継ぎデータを生成する。要求ごとに状態を作り、描画後に破棄する。生成済みのサーバーモジュールを再利用しても、可変状態を要求間で共有しない。

初期対応は共有ページに必要な入力、テキスト、属性、条件分岐、局所状態に限る。対応する記法と診断で拒否する記法を列挙し、全てのブラウザ向け記法をサーバーで扱う契約にはしない。ブラウザ専用の`onMount`、`effect`、`use=`はサーバー描画で実行しない。

SSRで動かすのは運営側が管理する共有ページの部品である。投稿されたJSXは部品として読み込まず、文字列データとして表示する。サーバーは保存・閲覧・削除・OGP生成のどの経路でも投稿ソースをコンパイル・実行しない。

### 初期応答と引継ぎ

1. 要求の共有IDを検査し、未削除の記録を一度取得する。権限確認後に表示用データを作り、同じデータから`head`、本文、引継ぎ用データを生成する。
2. 初期HTMLにタイトル、説明、ソース全文、コンパイラ版、作成日時、診断は「未実行」、プレビューは「実行すると表示」を含める。投稿由来の生成HTMLや画像は埋め込まない。
3. タイトル・属性・本文はそれぞれのHTML文脈でエスケープする。引継ぎ用JSONは管理鍵を除いた許可項目だけとし、`</script>`等で要素を脱出できない直列化を使う。
4. ブラウザは同じデータで既存DOMへ処理を接続する。hydrate（初期HTMLを再作成せず操作を接続する処理）の前後で、ソース、版、見出し、文字数が一致することを確認する。初回表示のためのAPI再取得は不要とする。初期編集欄は接続完了まで読取り専用にし、接続前に入力された内容を初期値で消す問題を避ける。
5. 編集開始後の下書き・実行番号・診断はブラウザが所有する。保存済みデータは変更せず、保存操作で新しい記録を作る。

### 本体変更の前に固定する事項

[ADR-0038](./adr/0038-client-build-ssr-boundary.md)に従い、次を新しいADRとOpenSpecへ記載してから実装する。既存のVite入口をSSR対応に見せかけるHTML置換は採らない。

- 運営側の部品をビルド時に処理し、要求時には入力データからHTMLを生成するサーバー入口を定める。要求時の再コンパイルを前提にしない。試作前に入力・出力・状態の契約を仮定義し、公開APIの名前は試作後に確定する。
- 要求ごとの状態を生成する単位、生成HTMLとブラウザ用モジュールの対応、JSONで引き継げる値の範囲を定める。関数・DOM・要求オブジェクトを直列化しない。
- module共有状態は初期のサーバー対象では診断で拒否する案から始める。共有状態の一般的な要求分離は、実例で必要になるまで追加しない。入力と部品の局所状態は要求終了時に解放する。
- `onMount`、`effect`、`use=`のブラウザ操作はサーバー描画時に実行しない。時刻・乱数等は初期描画中に再計算せず、必要ならサーバーで確定した値を引き継ぐ。
- 初期状態または生成物の版が不一致なら、接続を中止して再読込みを案内する。空の編集画面でソースを上書きせず、読取り用HTMLを残す。
- 404・503では正常ページ用の状態を生成しない。並行要求、途中の失敗、直後の正常要求でも状態が混ざらないことを試験する。

固定データをサーバーの文字列テンプレートで表示する試作は、配信・保存の確認には使える。ただし、Irisout生成のHTMLと引継ぎ経路が成立するまで「IrisoutのSSR利用例」は未完了とする。

## 8. 実装順序と各段階の完了条件

依存順序は`0 → 1`（文書公開）、`0 → 2 → 3`（ブラウザ実行）、`2 → 4 → 5`（共有SSR）とする。第5段階への着手には第3段階と第4段階の完了を条件とする。第1段階はSSRの成否に依存せず公開できる。第6段階は初回公開後に判断する。

| 段階                             | 作業と成果物                                                                                                  | 完了条件・次へ進めない条件                                                                                                                                                                                     |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0. 入力と範囲を固定              | 文書一覧、URL、例の一覧、対象版、暫定値の一覧を作る。作業単位ごとのOpenSpec changeを用意する                  | 既存文書の移動・参照方針が決まり、例が同じ版でコンパイルできる。本文と例に二重管理がない                                                                                                                       |
| 1. 文書のSSG                     | `app/web`に生成処理・文書画面・検索索引を追加し、サイト検査をCIへ接続する                                     | 初期掲載範囲が読み込める。JavaScriptなしの直接URL・目次・移動、参照切れ検出、依存の分離を確認する                                                                                                              |
| 2. 技術的な成立条件を検証        | ブラウザ用コンパイラ入口と隔離環境、Irisoutのサーバー用入口、異なる固定データ2件のSSR・引継ぎを別々に試作する | Node依存を含まないブラウザ生成物、隔離下のコンパイル・実行・停止、要求状態の分離を確認する。サーバー用入口のAPIと対応記法をADRとOpenSpecへ確定する。不成立なら共有機能を一般公開せず、この段階の設計を修正する |
| 3. 保存なしの編集・実行          | テキスト入力、例選択、実行・停止、診断、変更前表示、書き出しを接続する                                        | 構文エラー修正、時間超過後の再実行、旧結果の破棄、キーボード操作が動く。コンパイラ取得失敗でもソースを失わない                                                                                                 |
| 4. 保存・削除を内部接続          | SQLiteの形式、制限、再送、管理鍵、SSRへの記録読込みを実装する。運用設定を固定する                             | 保存→直接URL→複製保存→削除が動く。再送で重複・復活せず、通信断・再起動・保存先停止を処理する。公開の入口はまだ開放しない                                                                                       |
| 5. SSR共有ページを公開可能にする | 記録からIrisoutのサーバー用入口でHTML生成・引継ぎを行い、初期情報、限定公開、運用試験を揃える                 | 下の受入条件をすべて満たす。配信先、隔離用配信元、バックアップからの復元、削除の維持を確認して公開する                                                                                                         |
| 6. 公開範囲を拡張                | 公開一覧・認証付き非公開が必要な利用例を確認し、権限変更・検索・削除の設計を作る                              | 公開は掲載同意と通報対応、非公開は全読取り経路の認証と所有確認を条件に、別のADR・OpenSpecで実装する                                                                                                            |

第2段階ではCounterに加え、初期文字列・条件分岐・局所状態を含む固定ページを使う。初期データAとBを交互・並行に要求し、片方の値・診断・状態がもう片方へ出ないことを確認する。全ての既存記法のSSR対応を一度に約束しない。必要な記法と拒否する記法を仕様へ列挙する。

## 9. 受入条件と検証方法の案

本表はOpenSpecへ移す前の検証計画である。実装開始後の受入条件の正本は`openspec/specs/`とする。

| ID  | 条件                                   | 検証方法                                                                                                                                         |
| --- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | 全文書がJavaScriptなしで読める         | 本番配信へ直接アクセスし、本文・コード・目次・前後リンク・モバイル一覧を操作する                                                                 |
| D2  | 不正な文書を公開しない                 | 重複slug、見出し参照切れ、不明な例、任意HTMLを含む入力でビルドが失敗する                                                                         |
| D3  | 文書と編集機能の依存が分かれる         | 配信物の依存一覧と通信記録で、解析器・強調表示器の不在、文書閲覧時のコンパイラ未取得を確認する                                                   |
| P1  | 対応記法をブラウザ内で変換できる       | 同じ版・同じ公式例で既存入口と結果・診断を比較し、ブラウザ生成物のNode依存を検査する                                                             |
| P2  | 実行状態が混ざらず復旧できる           | 構文エラー、初期化例外、無限ループ、連続実行、停止、古い応答、読込み失敗を操作する                                                               |
| P3  | 投稿コードが公式サイトの権限を使えない | 親DOM・保存領域・Cookieへの接触、管理鍵要求、外部通信、上位遷移、偽メッセージを試行する。制約も記録する                                          |
| S1  | ソースを保存・共有・削除できる         | 保存後の直接URLと再起動後の読取り、複製の独立性、正誤の管理鍵、削除後の404を確認する                                                             |
| S2  | 入力制限と再送契約が守られる           | 日本語での文字数・バイト数境界、不正JSON、未知の版、413・429・503、応答喪失後の再送、削除後の再送を確認する                                      |
| R1  | ビルド後に作ったIDを要求時に描画する   | サイトをビルドしてから記録を作り、再ビルドなしで200と初期HTML、未存在IDで404を得る                                                               |
| R2  | 初期HTMLと引継ぎが一致する             | JavaScript無効時のタイトル・説明・全文・版を取得し、有効時に同じDOMが接続され編集できることを確認する                                            |
| R3  | 要求ごとの状態が混ざらない             | A/Bの並行要求、片方の失敗、次の要求を検査し、ブラウザの片方の編集が他方へ波及しないことを確認する                                                |
| R4  | 保存値がHTMLやスクリプトにならない     | タイトル・説明・ソースに閉じタグ、引用符、`</script>`、イベント属性を含め、初期HTMLと引継ぎ後の非実行を確認する                                  |
| R5  | サーバーが投稿ソースを実行しない       | 保存・閲覧・削除で、コンパイルすると副作用を起こす入力が実行されないことを隔離した試験環境で確認し、各経路にコンパイラ呼出しがないことも確認する |
| O1  | 公開後に削除と復旧ができる             | 保存先障害、バックアップ復元、削除記録の再適用、隔離配信停止、保存停止を予行する                                                                 |

画面の試験には、キーボードでの全操作、入力欄とiframeの名前、診断通知、フォーカスの維持、横幅360pxでの操作を含める。ブラウザは実施時のChromium・Firefox・WebKitの版を記録し、第2段階では隔離と引継ぎを、第5段階では保存・削除を含む操作を確認する。

既存の検査入口は`bun run check`、`bun run test`、`bun run build`、`bun run build:web`とする。本体・公開入口を変更する段階では`bun run build:packages`、`bun run pack:smoke`も実施する。サイトの文書・API・ブラウザ検査は各段階で実行スクリプトを追加し、CIから実際に呼ぶところまでを完了条件に含める。

性能は文書閲覧とPlayground起動を別々に記録する。文書のHTML/CSS/JavaScript転送量、コンパイラの初回転送量・起動時間、公式例のコンパイル時間、共有ページの応答時間を同じ環境で測定する。未計測の速度やサイズを目標値として断定せず、第2段階の結果から公開時の上限を決める。

## 10. 公開前の決定事項と運用

| 決定事項                               | 期限            | 判断に使う材料                                                       |
| -------------------------------------- | --------------- | -------------------------------------------------------------------- |
| Markdown解析器・強調表示器             | 第1段階の実装前 | 任意HTMLの拒否、見出しID、採用言語、日本語、ビルド依存への限定       |
| ブラウザ用入口・SSRのAPIと対象記法     | 第2段階の試作後 | 固定ページで必要な入力と状態、既存入口の回帰検査、生成物の依存       |
| 隔離用配信元とCSP                      | 第2段階の完了前 | Worker起動、生成コード読込み、通信・遷移・権限の試験結果             |
| 配信先・永続保存先                     | 第4段階の着手前 | Bun実行、SQLiteと永続ディスク、隔離配信、バックアップ手段            |
| 保存量・要求頻度・管理鍵の保持         | 第4段階の完了前 | 入力上限での容量見積り、共有回線の誤制限、送信元情報、鍵紛失時の案内 |
| 保存期間・削除記録・バックアップ保持   | 第5段階の公開前 | 削除済み共有を復元で再公開しない手順、再送の識別期間、説明文         |
| 旧コンパイラ版の保持と停止             | 第5段階の公開前 | 再現性、脆弱性対応、停止後もソースを読める経路                       |
| 通報・管理者削除・保存停止の担当と手順 | 第5段階の公開前 | 匿名保存の悪用対応、全体容量上限、誤削除時の扱い                     |

公開前にデータベースの作成・移行・復元手順と、アプリを前の版へ戻す手順を記録する。静的生成物・サーバー・コンパイラ資産の版を合わせ、既存の共有形式を読めない変更は移行手順なしで配信しない。

監視対象は保存・削除の失敗数、404と503の件数、制限発動数、データベース容量、応答時間とする。ソース・説明・管理鍵・認証ヘッダーはログへ記録しない。初期のキャッシュ追加は文書と版を固定した資産だけとし、共有ページの高速化は測定後に判断する。

文書公開だけを行う場合は保存APIを有効にしない。共有機能の障害時は新規保存を停止できるようにし、ソース閲覧・書き出し・削除を可能な範囲で維持する。バックアップから戻す場合は、運用を再開する前に削除記録を適用する。

## 11. 対象外

- YouTube APIから取得した利用者データの公開ページ。
- 投稿コードのサーバー実行、サーバーでの診断生成、プレビュー画像生成。
- 複数人の同時編集、既存IDの上書き、アカウントごとの作品管理。
- 文書を要求ごとのSSRへ移すこと、サイト全体の単一ページアプリ化。
- 汎用的なSSR基盤、任意依存の取得、利用例のないコンパイラ機能の追加。

次の着手単位は第0段階の文書一覧・例・入力形式の確定とする。続いて第1段階のSSGを作り、第2段階でブラウザ実行とSSRの成立条件を検証する。以降の実装状況は[STATUS.md](../STATUS.md)、判断待ちの論点は[ROADMAP.md](../ROADMAP.md)、決定はADRへ記録する。
