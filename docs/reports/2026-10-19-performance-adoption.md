## 次の測定

再開の条件は、利用例に必要な改善量と他指標の許容量を再測定前の計画として決め、両版を同じ環境で構築できることとする。候補を変更する場合は実装前に決める。主指標の候補は固定位置交換の同期時間だが、実用上必要な絶対短縮量、描画込みの許容増加、非対象操作の許容増加、保持メモリの許容増加、gzip/Brotliの許容バイト数が未設定である。これらは利用例から決め、未設定のまま再開しない。時間の比率を主指標に選ぶ場合は、その区間も算出する。

1. 今回の追加変更だけの効果を測る場合は、以下の2つの作業木を使う。現行版の評価は別に基準を固定し、この旧版の値と混ぜない。同じ機器とChromeの実行ファイルを両方へ指定し、Bun・Node・OS・依存の固定ファイル・上流の版・生成物のハッシュを保存する。

```sh

git worktree add --detach /tmp/irisout-adoption-after 72b9bf4
```

それぞれの作業木で`bun install --frozen-lockfile`と`setup.mjs`を実行する。上流の準備先も分ける。`setup.mjs`は全比較実装を準備するため、途中で対象を絞らない。

```sh
# /tmp/irisout-adoption-before で実行

JSFB_CHECKOUT=/tmp/irisout-adoption-upstream-before bun packages/bench/js-framework/setup.mjs
# /tmp/irisout-adoption-after で実行
bun install --frozen-lockfile
```

両方の`dist/assets/*.js`のSHA-256を冒頭の値と照合する。一致しなければ過去の生成物を再現できていないと記録し、過去の標本と合算しない。依存・構築条件を揃えて新しい前後の基準を固定し直す。JSXと明示的な`listEvents: 'delegated'`は両版で揃え、既定の直接配線の値を混ぜない。

2. 準備した上流サーバーを別端末で起動する。出力中の参照先を変更してハッシュを変えないよう、別ポートで同じ経路を配信する。以下のコマンドは当時の値を再現するための条件であり、今回は実行していない。

```sh
# /tmp/irisout-adoption-upstream-after/server で実行
```

評価用の作業木のルートで次を実行する。先に`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`へ使用するChromeの絶対パスを設定する。全9操作を各100試行、独立した3つのブラウザー起動で測る。組2は最初の実装順を反転し、各組内でも順序を交替する。出力名は未使用のものに替え、過去のJSONを上書きしない。

```sh

  reverse=0
  if [ "$group" = 2 ]; then reverse=1; fi
  JSFB_PROBE_SAMPLES=100 JSFB_PROBE_CPU_RATE=1 JSFB_PROBE_REVERSE="$reverse" JSFB_PROBE_OUTPUT="packages/bench/js-framework/adoption-sync-$group.json" bun packages/bench/js-framework/probe.mjs http://localhost:8095/frameworks/keyed/irisout/dist/index.html http://localhost:8096/frameworks/keyed/irisout/dist/index.html
```

各JSONの`artifacts`・`browser`・`cpu`と各操作の前後100標本を照合する。組ごとに既存の`notification-report.mjs`と同じ対応標本の再抽出法で絶対差と区間を求め、比率も示す。既存の集計器は過去のファイル名・ハッシュを固定しているため、そこを新しい結果で置換しない。新しい結果の集計は別の出力へ残す。Vanilla比較を加える場合も別の100試行を保存し、前後の確認3組の代わりに数えない。

3. 同期測定を終えたら両サーバーを停止する。各作業木で、対応する`JSFB_CHECKOUT`と未使用のタグを指定して、以下の公式測定と集計を行う。下例は修正前の第1組であり、修正後は`after`の作業木・準備先・タグを使う。


第1組は修正前→修正後、第2組は修正後→修正前の順に逐次実行し、第2組では`JSFB_REVERSE_FRAMEWORK_ORDER=1`で公式サーバーの実際の列挙順も反転する。CPU各10試行（選択20試行）とメモリ各3試行を各組で保存する。メモリは起動後・作成後・作成削除5回後を区別し、JavaScriptだけの保持量とは呼ばない。描画込みのCPU値は前後を独立に再抽出して差の区間を求める。gzipは同期JSONのスクリプト量、Brotliは公式測定のHTML等を含む転送量であり、対象範囲を揃えた前後比較だけを行う。

4. 追加計測はまず上記の同期3組と公式2組までとする。そこで事前の必要量を区間まで含めて満たし、他指標も許容量内、正しさも通過した場合だけ採用を再検討する。機器・ハッシュ・試行数の不一致やブラウザー終了があった組は理由を残して組全体を取り直し、性能の結論を得るための無制限な追加試行は行わない。再測定後も効果を確認できず、増加した転送量・保持状態・復旧分岐を正当化できなければ、この追加最適化の展開を不採用とする。許容外の悪化または正しさの破壊が確認された場合も不採用とし、既存コードへ戻す差分と回帰試験を個別に作る。過去の一覧最適化全体は一括で戻さない。
