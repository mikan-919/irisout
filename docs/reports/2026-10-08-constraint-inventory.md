# irisout 拒否条件の整理

初期化本体の途中返却の制限は、後続の[初期化関数の制御フロー](./2026-10-09-lifecycle-control-flow.md)で解消した。この文書の表と試験件数は前段の記録を保持する。

調査対象は `packages/compiler/src`、`packages/vite-plugin/src`、`packages/hono/src`、`packages/runtime/src` と `openspec/specs`。以下の表は2026-10-08の作業開始時点（`da83fa8`）の調査を保存したもの。表の行番号と拒否条件は変更前を指す。この調査後の変更を次に記載する。

## この変更で解消した制限と不具合

G01の文種の許可表を除去し、ハンドラーと内部関数のループ、switch、例外処理、var、関数・クラス宣言を受理した。G02の通常の関数の値付きreturnと書込み後returnの禁止を除去し、関数の出口から状態を反映する。G03は解析した局所関数の直接呼出しを受理した。解析を共通化し、重複していた式・文・補助関数の変換を削除した。

非同期補助関数と補助関数内部のPromiseコールバックの更新漏れ、Promiseコールバックの返り値の消失、signal書込み式の演算子の優先順位を修正した。内部関数の作成時には、その書込みを理由とするeffectの再実行を起こさない。所有範囲とeffectの禁止検査には、非同期処理も含む全書込み集合を使い、実行時の反映集合とは分ける。

受入試験は新規20件と既存試験の変更を含む全376件。Chromiumの8項目の操作検査と、保存した検査器の再実行が成功した。型検査、実例の構築、公開物の構築と梱包物の別ディレクトリ導入検査、文書検査も成功した。ブラウザー操作は[結果](./evidence/2026-10-08-handler-browser.json)、再実行は[検査器](../../fixtures/handler-control-flow/README.md)を参照する。画像の比較と性能の比較はこの変更では行っていない。

## 残る制限

- G02: アクションとonMountの初期化本体は、末尾の返り値を分離している。途中の値付きreturnと、書込みまたは追跡補助関数呼出し後のreturnはまだ拒否する。
- G03: 引数や別名に保存した関数値の直接呼出しなど、解析した関数本体へ解決できない呼出しには制限が残る。
- G04: 生成名との衝突はまだ拒否する。イベントの引数も識別子一つに限る。
- 関数出口への反映で扱えない実行境界: ジェネレーターと、既定引数・クラスフィールド・計算されたメソッド名の状態API参照は別途変換が必要。これまで黙って不正な呼出しを出力した箇所を診断へ変更した。既定引数や計算メソッド名の内部関数を経由する参照も検査する。
- 同期補助関数では、呼出し式の評価開始時に更新対象とする静的な過剰近似が残る。引数評価が例外で終わった場合も更新処理を呼びうる。直接setterは代入成功後だけを更新の根拠とする。
- この表のその他の群は残る。未対応のJSX記法、状態APIの形、サーバーとブラウザー間のJSON境界などを解消したとは主張しない。

注: 以上は未公開のソース変更であり、npm公開版0.3.7への変更ではない。現在の関数本体の対応範囲は[イベントとアクション](../events-and-actions.md)、設計判断は[ADR-0065](../adr/0065-function-body-updates.md)、受入条件は`openspec/specs/`を参照する。

## 調査開始時の分類

エラーの文字列数は利用規則の数ではない。同じ引数検査が式・文・入れ子関数へ複製されている。内部整合性検査、例外の再送出、生成コード内の検査もある。利用者へ説明する境界と、削除する実装制限を区別する。分類の「設計上の境界」は現行設計によるものであり、永久に維持すべきという意味ではない。

## 方針

最初に通常のJavaScriptの制限を除く。ハンドラーと補助関数の `for`、`while`、`switch`、`try`、`throw`、`var`、関数宣言、値を返す `return` は、UIの依存先を決める規則ではない。書込み後に更新関数を呼ぶ生成方法の制限を利用者へ転嫁している。関数の出口や書込みへ更新処理を挿入すれば解消できる。書込み対象の収集、例外、早期返却、非同期再開、入れ子関数の所有範囲をそれぞれ検証する必要がある。

残す説明は具体的な契約にする。状態は `signal` の読み書きと `derived` の読み取り、UIはJSXの要素・式・条件・配列、外部処理の生存期間は `onMount`/`effect`/`use`、サーバーとブラウザーの搬送値はJSON、という対象ごとの契約である。「静的解析できるものだけ」という説明では、普通のJavaScriptの何が受理されるか決められない。

## 実装と仕様の差

照合の証拠と範囲は[仕様の照合](./evidence/2026-10-08-constraint-spec-evidence.md)へ保存した。既存10試験で裏付けられたルート状態参照、外部・資源import、構造の深さの矛盾を正本へ反映した。SSRの相対module対応に関する文書と注釈も修正した。構造単位の拒否診断は、実際の条件である字句スコープ外の局所状態参照へ限定した。以下は調査開始時に見つけた差の記録である。

1. `same-file-component-composition:142–170` のルートsignal参照拒否は現行条件と矛盾する。`render.ts` はrootをnestedDepsに持ち上げ、別局所scopeのみを拒否する。メッセージ二箇所も実際より広い拒否を示す。
2. `multi-file-module-composition:60` の外部specifier拒否は現行実装と矛盾する。外部importとVite資源は保存される。相対namespace/副作用importだけがリンク制限である。
3. module-linkerのtype-only import/export拒否は、stripTypeScriptによる先行除去後では通常到達しない。型importを一律未対応と説明しない。
4. `source.ts` のhasRelativeModuleオプションは現状SSR拒否に使われない。『SSRは単一ファイル』という注釈は制約として残さない。
5. `parseSignalDeclStatement` はconst/let/varのkindを検査しない。一文一宣言、直接API呼出し、識別子、引数数は検査する。const必須という仕様と現行拒否条件を分ける。
6. `same-file-component-composition:38` の『深すぎるネスト』は現在の無制限再帰構造と矛盾する。構造の深さを数値で制限する明示拒否は見つからない。
7. actionとlifecycleの『ゼロ引数返り関数』の制約はコンパイル側の直接関数式を検査する。runtime normalizeUseActionResultは関数のlengthを検査しない。構文制限と実行時shape保証は同一ではない。
