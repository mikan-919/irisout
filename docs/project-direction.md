# irisout 開発方針

策定日: 2026-09-07。対象はTypeScript版のコンパイラ、実行時処理、Vite連携、利用例である。
開発順序と完了条件は[ROADMAP.md](../ROADMAP.md)、実装状況は[STATUS.md](../STATUS.md)に置く。

## 到達点

irisoutを、文章処理、フォーム、一覧操作などのブラウザ内ツールをJSXで記述し、静的HTMLと直接DOM更新コードとして配布できる開発基盤にする。次の到達点は、作者以外の開発者が別のリポジトリへ導入し、画面と処理を分割して実装し、エラーの原因を元のコードから調べられる試用版である。

情報量ヒートマップを継続利用し、そこで生じる記述上の制約と生成物の問題を改善する。TodoMVCとnotesも併用し、文章解析に固有の都合がコンパイラ全体の仕様にならないよう判断する。利用者数や開発人数の情報はないため、外部利用の需要は今後の試用で確かめる仮説として扱う。

注: 直接DOM更新とは、ブラウザが保持する要素やテキストを書き換える方式を指す。JSXは画面構造をJavaScript中へ記述する構文であり、Reactとの互換性を意味しない。

計測値は記載日の環境と入力に限る。TodoMVCは生成版の初期HTML構築を計時外とし、手書き版とReact版は空の要素から生成しているため、ページ表示全体の比較値ではない。ヒートマップの値は単一のLinux・Chromium環境での中央値であり、WorkerのメモリとDOMの内部メモリを含まない。現行版の性能改善に着手するときは基準値を取り直す。

## 開発の優先順位

1. 状態更新の欠落、不正な生成コード、破棄漏れ、初期HTMLと更新結果の不一致を修正する。未対応構文はコンパイル時に場所と理由を示す。
2. 利用例で必要になった部品分割、入力、非同期処理の記述を整える。既存記法で表せる場合は利用例と文書を改善し、表せない場合に仕様を検討する。
3. 初期化時間、更新時間、転送量、メモリを測り、原因が確認できた処理を改善する。
4. 対応範囲、導入手順、配布物、変更履歴を揃え、外部での試用へ進む。

不具合は、利用例の追加や配布準備より先に扱う。性能改善は既存機能の動作と未使用機能の除外を保つことを条件とする。整理のための内部変更は、対象の修正や検証に必要な範囲で行う。

## 性能最適化の採用基準

2026-10-19以降の性能最適化は、次の手順で採用・保留・不採用を判断する。[一覧高速化計画の検収条件](./reports/2026-10-16-list-performance-plan.md#検収)を共通の判断手順へ広げたものであり、過去の採用記録や測定値を書き換えない。個別の生成方式の設計判断は引き続きADRへ置く。

実装前に、対象の利用例、入力と操作、基準コミットと生成物のSHA-256、比較候補、測定環境、主指標、実用上必要な改善量を記録する。改善量は対象の利用で必要となる絶対量または比率で定め、値を見た後で下げない。同期処理、描画込みの操作時間、起動・作成後・削除反復後の保持メモリ、生成物と転送量（gzip・Brotli）のうち、主指標以外に許容する変化も単位付きで事前に定める。測らない指標はその理由と判断を制限する範囲を書く。正しさの破壊は許容しない。

比較は同じ入力、操作、ブラウザー版、機器、実行設定で行い、実装順を交替する。基準と候補の生成物、依存の固定ファイル、入力、測定器の識別情報を保存し、途中で変わった値を合算しない。同期した処理とDOM書込みは、配置計算・描画を含む時間と分ける。処理回数の計装と時間測定、他の負荷は並行させない。試作の選別に使った値とは別に、独立した再測定を行う。

一覧の比較では、既存計画に従い同期全9操作を独立3組・各100試行、各組で事前3回と実装順の交替を行う。公式測定はCPU各10試行（選択20試行）・メモリ各3試行以上・転送量を用い、実際の実装順を変えた組も保存する。別の利用例では必要な精度と負荷から回数を実装前に定める。各組の中央値、絶対差、比率、試行数、差の95%区間と算出法を記録する。追加試行の上限・再測定の条件も先に定め、都合のよい組だけを採らない。

注: SHA-256は生成物の内容を照合する値である。95%区間は標本から推定する差の不確かさを示し、対応する同期試行の組を再抽出する方法と、独立した公式試行を別々に再抽出する方法を区別する。同じ標本の再集計は独立した再測定ではない。組をまたぐ機器の状態差や、複数操作を比較して都合のよい結果を選ぶ問題までは、この区間だけで取り除けない。

| 判断   | 条件と次の扱い                                                                                                                                                                                                                                                                                         |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 採用   | 正しさを保ち、独立した確認の各組で主指標の改善が事前の必要量を満たす。差を候補−基準とした場合、95%区間の上端まで必要量を満たすことを確認する。他指標も事前の許容量内である根拠を示し、生成コード・分岐・保持状態・復旧経路・試験の複雑さに見合う効果を記録する。採用範囲は測った利用例と適用条件に限る |
| 保留   | 区間が必要量の境界をまたぐ、組によって結論が異なる、他指標や実用上の必要量が未確認など、採否に必要な証拠が欠ける。追加展開を止め、基準と候補、測り直す条件、試行数と上限、不採用へ戻す条件を記録する                                                                                                   |
| 不採用 | 正しさを壊す、許容外の悪化が確認される、または事前に定めた再測定を終えても必要な効果を確認できず、複雑さや資源増加を正当化できない。候補を展開せず、既存実装を戻す場合も対象差分と回帰試験を分けて判断する                                                                                             |

区間が0を含むことは、同等・改善・目標達成の証明にしない。同等性が必要なら、事前の許容幅へ区間全体が収まるかを評価する。比率を主指標にする場合は比率の区間も求める。複数操作の各95%区間は全操作を同時に保証しないため、主指標を先に限定し、全操作について結論を出す場合の多重比較の扱いも事前に決める。単一操作の短縮や処理回数の削減から、全操作・全環境で最速とは主張しない。

初回の適用は[通知・固定位置交換の評価](./reports/2026-10-19-performance-adoption.md)に記録する。

## 継続する設計判断

[CONCEPT.v3.md](../CONCEPT.v3.md)の静的解析、直接DOM更新、使用した機能に必要な実行時処理だけを含める方針を維持する。専用コードの生成と共有処理のどちらを使うかは、動作、速度、サイズ、メモリ、保守に必要な作業を比較して決める。

コンパイル対象の部品と、通常のJavaScript・外部ライブラリの境界を維持する。解析アルゴリズム、要求番号、古い結果の破棄、文章指標の定義はアプリ側で扱う。状態とDOMの接続、部品の展開、初期化と破棄の接続はコンパイラ側で扱う。

初期HTMLはビルド時に生成し、ブラウザでイベントと状態更新を接続する。[ADR-0038](./adr/0038-client-build-ssr-boundary.md)に従い、要求ごとのサーバー描画は別の設計課題とする。

注: 初期HTMLへの接続をhydrateと呼ぶ。ソースマップは、生成後のコードの位置と元ファイルの位置を対応付け、例外や停止位置を調べるための情報である。

## 追加機能の採否

新機能の提案には、現在のコードで困る例、既存記法での代替、生成コードへの影響、対応しない範囲を添える。採用時は[設計判断記録](./adr/)と[仕様](../openspec/specs/)へ反映し、一つの利用例と試験で確認できる単位に分ける。

| 候補                                          | 着手する条件                                                                             |
| --------------------------------------------- | ---------------------------------------------------------------------------------------- |
| propsの既定値・別名、部品間の子要素の受け渡し | ヒートマップのファイル分割で制約を再現し、静的な式の置換で扱う範囲を決められる           |
| `try/catch/finally`などのハンドラ構文         | 成功・失敗・終了処理の利用例があり、例外と途中終了を含む状態更新のタイミングを定義できる |
| `.ts`/`.tsx`入力                              | 試用でJSDocによる型記述が導入や保守を妨げる事例が得られる                                |
| 編集時の状態保持                              | ページ再読み込みによる入力のやり直しが作業を妨げ、状態の移行と破棄の規則を決められる     |
| 表示範囲を限定する一覧、要求処理の中断        | 入力上限内でもDOM数や古い要求の待ち行列が操作を妨げると計測で確認できる                  |
| 画面遷移、保存、外部サービスとの通信          | 試用するアプリが必要とし、ブラウザ標準機能や外部処理との組み合わせで不足する箇所を示せる |

`bind:value`は2026-09-07に実装を取り消した履歴がある。取り消し理由はコミットからは確定できないため、復活を予定へ含めない。フォームは現行の`value`/`checked`とイベント処理を基準に検証する。

PDF抽出、学習済みモデル、要求ごとのサーバー描画、汎用の非同期実行基盤、アニメーション、別DOM領域への描画、部品単位の例外回復は、今回の試用版の完了条件に含めない。必要になった利用例と既存仕様への影響を確認して再検討する。

## 方針を見直す時点

利用例で回避している制約、再現できる不具合、性能値、導入試験の結果を確認してから次の変更を選ぶ。`irisout` 0.3.0は2026-09-26にnpmへ公開済みで、作者以外の人間による手動試用は行っていない。安定版の互換性保証は、作者以外の外部導入の検証後に決める。
